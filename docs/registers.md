# Register accesses of the FireGL kernel object and X module

Every memory-mapped register access that the kernel object `fglrx.o` and the X module `fglrx_drv.so` make
through a register aperture, by offset: width, direction, the routines that make it, and the public register at
that offset when there is one. The tables come from the replay in `retools/tools/inventory.py` (the register-window
section of `scripts/inventory-config.json`) and are regenerated by `retools/tools/voyager/register_table.py`; the
per-offset inventory rows are in [inventory/mmio.tsv](inventory/mmio.tsv).

Offsets are byte offsets from the start of the register aperture: BAR 2, the 64 KB register window the kernel
attach path maps with the word-values flag ([kernel-attach.md](kernel-attach.md), step 5). The X module maps the
same BAR itself.

## Sources

- The shipped objects: `fglrx.o` (a 64-bit relocatable MIPS object) and `fglrx_drv.so` (an n32 shared object).
  The kernel object is read at its section offsets, the X module at its dynamic-symbol addresses.
- Public register names from the Linux radeon driver (`reg_srcs/r300`, `r300d.h`, `r100d.h`, `r300_reg.h`,
  `radeon_reg.h`) and Mesa's `r300_reg.h`, at the pins of the `linux/` and `mesa/` submodules. AMD's R3xx 3D
  register reference (listed in [sources/INDEX.md](sources/INDEX.md)) was not read for this table: it covers
  the 3D block, and the offsets here are mostly the display, interrupt, clock and engine-status registers.
  Linux and Mesa show what the public chips do, not what IRIX does on this board.

## How the code reaches the registers

All of it is established from the disassembly.

- **Kernel object, board record.** The board record holds the mapped register aperture as a 64-bit pointer at
  +656. `fglrx_attach` at 0xbdc, `fglrx_intr` at 0x964, `fglrx_exit` and `fglrx_dma_flush` load it and use
  constant offsets from it.
- **Kernel object, device record.** `firegl_addmap` at 0x1bc50 stores the mapped register aperture at device
  record +1000 (instruction 0x1c2b8) and reads the word at 0xf18 from it at once. The `_r6x_*` routines, `firegl_sync_dacs`
  and the interrupt routines load it from there.
- **Kernel object, accessors.** `FGLRXReadRegister` at 0x4908 and `FGLRXWriteRegister` at 0x4950 take a board
  index and a byte offset, look the board up in `fglrx_boards`, load the aperture from board record +656, and
  do one 32-bit load or store. `FGLRXWriteRegister8` at 0x49a0 has the same shape and also stores a 32-bit word,
  not a byte. All three return 5 when the board has no aperture. `FGLRXINPLL` at 0x49f0 takes a board index, a
  PLL index and the byte offsets of the index and data registers: it writes the index masked to six bits with
  `FGLRXWriteRegister8`, then reads the data register with `FGLRXReadRegister`. The addresses of these routines
  sit in `.rodata` at 0xc30 and 0xc38 (and those of the next pair at 0xe80 and 0xe90) as relocated pointers, so
  they are called through a table from outside the object; no routine of `fglrx.o` calls `FGLRXINPLL`.
- **Kernel object, dword accessors.** `fglrxReadMmRegister` at 0x5480 and `fglrxWriteMmRegister` at 0x554c take
  the aperture base and a dword index, scale it by four, and accept only the indexes 184, 185 and 186 (byte
  offsets 0x2e0, 0x2e4 and 0x2e8); any other index calls a helper with message strings and returns zero. `fglrxCompositorI2cRegRead` at 0x5738 is their
  only user (see Not in the tables).
- **X module, driver record.** The screen record's private pointer at +248 leads to the driver record, and the
  mapped aperture is the 32-bit pointer at +48 of that record (`lw s1,248(a0)` then `lw s0,48(s1)` at 0x4441e0
  and 0x4441e8 in `Set_MV_Mode`). Routines use constant offsets from it, with plain word loads and stores and
  no byte swapping in the code.
- **X module, PLL helpers.** `ulRC6PllReadUlong` at 0x42e940 and `vRC6PllWriteUlong` at 0x42e980 take the
  aperture base as their first argument and use the words at +8 and +12 as an index and data pair.
  `R200INPLL` at 0x410dc0 stores the index masked to six bits as a single byte at +11 (the last byte of the
  dword at 0x8) and reads the word at +12.

Narrow accesses are graded as a lane of the dword they sit in: the byte store at 0xb is a store to the index
register at 0x8, and the byte store at 0xb3 a store to the palette index register at 0xb0.

## Grades

The public-name grade compares the offset with the tables above.

- `exact`: one name at the offset in a table written for the R3xx (`reg_srcs/r300`, `r300d.h`, `r100d.h` or
  `r300_reg.h`) and no table disagrees.
- `common`: one name, found only in `radeon_reg.h` or Mesa. These are registers the earlier chips share, and
  Linux uses them for the R3xx.
- `conflict`: the tables put different names at the offset; all are listed. Behaviour in the code settles some
  of them below.
- `lane`: a byte or halfword access inside the named dword.
- `none`: no public table has the offset.

A grade says the offsets match. It does not say the code uses the register as the name suggests; the section
after the tables reads a set of registers against their bit definitions to check that.

## Access tables

The tables list every offset the replay resolved. Each row stands for a register the code reaches through the
configured base. Rows of the X module count dummy reads (loads into register zero, used to flush a posted
write) as reads.

The last column says how far the register's role is read. `see below` means a section after the tables reads the
register against its bit definitions. `unknown` means no such section exists yet: the access count and the routine
name say where the register is reached, not what it is for. One test settles any `unknown` row. Run
`retools/tools/hostfacts.py` on the row's routine, and on the further routines the inventory in `docs/inventory/`
lists for the offset. List the stores to the offset, with the constants and conditions that reach them, and compare each
stored mask or value with the public bit names for that offset (the AMD register references indexed in
`docs/sources/INDEX.md`, Linux's `radeon_reg.h` and `r300_reg.h`). Then write the role up as an entry under
"Registers read in full"; regenerating the tables turns the cell to `see below`. A role that rests on board wiring or
silicon behaviour the code cannot show stays unknown until a vendor reference for this chip exists, and its entry says
so.

## Registers read in full

Each entry below was read against the bodies of the routines it cites and against the bit definitions in the
public headers it names. The entries for `fglrx.o` come first, then those for `fglrx_drv.so`, each in offset order.

- **0x28** in `fglrx.o`: a read of the scratch register the public headers call `BIOS_6_SCRATCH` (common).
  `_r6x_CheckWSBoard` at 0x13aa8 tests bit 13 of it, only when the board record's identifier at +28 equals
  0x85000004 or 0x8820ffff, and then sets flag 0x10 in the board record at +16. The public headers define no
  bit 13 for this register. Inferred.
- **0x40** in `fglrx.o`: the public `GEN_INT_CNTL` (exact). `fglrx_attach` at 0xbdc stores zero to it after
  programming the tile configuration, `fglrx_intr` at 0x964 clears bits 2 and 6 with the mask 0xffffffbb on the
  path taken when board record +792 or the board table slot is zero, and `_r6x_enable_vsync_irq` at 0x20cb0 ORs a word from the global `irq_table` (`.data` at 0x9b8, 624 bytes, 26 entries of 24 bytes, three words each) into it: the third word of entry 0, which is 1, so it sets bit 0. Bits 2 and 6 are the vertical-sync enables of the first and second CRTC in `r100d.h`, and bit 0 is `CRTC_VBLANK`; Linux's R300 code path uses the same layout (its R300 interrupt-set routine is the R100 one, which sets `CRTC_VBLANK` and `CRTC2_VBLANK`, bits 0 and 9, for a vertical-blank interrupt). AMD's R3xx 3D reference and R5xx acceleration guide do not list this register, and the M56 reference lists a `GEN_INT_CNTL` only in the video-input block at 0x100, without these display bits, so the names rest on the Linux and X.Org headers. Established for the offsets and bits read; the bit names are the public ones.
- **0x44** in `fglrx.o`: the public `GEN_INT_STATUS` (exact). `fglrx_intr` at 0x964 reads it, tests bit 2 (the
  first CRTC's vertical-sync status in `r100d.h`) and acknowledges by writing 4. `_r6x_service_irq_vsync_handler`
  at 0x20b08 reads it, ANDs the value with the first word of `irq_table` entry 0 (1) and, when that is nonzero, writes the
  value ORed with the entry's second word (1) back, so it tests and acknowledges bit 0 only (`CRTC_VBLANK_STAT` and its acknowledge in `r100d.h`). Established.
- **0x50** in `fglrx.o`: the public `CRTC_GEN_CNTL` (exact). `fglrx_attach` at 0xbdc reads it, ANDs it with
  0xfdfeffff and writes it back, which clears bit 25 (the CRTC enable) and bit 16 (the cursor enable) in `r100d.h`.
  `firegl_sync_dacs` at 0x1f5e8 reads and writes it too, with a mask that is not read. Established for
  `fglrx_attach`.
- **0xe4** in `fglrx.o`: a read of the public `CONFIG_XSTRAP` (common). `_r6x_CheckWSBoard` at 0x13aa8 tests bit 27
  of it and sets flag 0x10 in the board record at +16 when it is set. Established. The M56 Register Reference Guide (RRG-216M56-03oOEM, a later part) lists `CONFIG_XSTRAP` at VIPDEC 0xe4 (page 2-144) with fields only in bits 9:1; it defines no bit 27, so it neither confirms nor contradicts the test.
- **0x294** in `fglrx.o`: no public table has it. `_r6x_EnableStereo` at 0x13b4c sets bits 13 and 12 (0x3000)
  with a read-modify-write when its second argument is nonzero and board record flag 0x20 at +16 is set, clears
  them with the mask 0xffffcfff when the argument is zero, and issues a `sync` after each store. Established. The register's name is open.
- **0x3f8** in `fglrx.o`: the public `CRTC2_GEN_CNTL` (exact). `fglrx_attach` at 0xbdc applies the same 0xfdfeffff
  mask to it as to the first CRTC's register, clearing bit 25 (the second CRTC enable) and bit 16 (its cursor
  enable) in `r100d.h`; `firegl_sync_dacs` at 0x1f5e8 also reads and writes it. Established for `fglrx_attach`.
- **0x7c0** in `fglrx.o`: the public `CP_STAT` (exact). `_r6x_resetPM4` at 0x135fc re-reads it until bit 30
  clears (`CMDSTRM_BUSY` in `r300d.h`) before it touches the engine. Established.
- **0xe40** in `fglrx.o`: the public `RBBM_STATUS` (exact). `_r6x_resetPM4` at 0x135fc reads it five times and
  tests bit 31 (`GUI_ACTIVE` in `r300d.h`) after the command stream drains. All five reads use the same mask,
  0x80000000 (`lui a1,0x8000`, set at 0x136f4): the first read at 0x136f0 leaves the wait when the bit is clear,
  and the four reads at 0x13704, 0x13714, 0x13724 and 0x13734 are one loop unrolled four times, which repeats
  while the bit is set. No other bit of the register is tested in this routine. `__fglQSQuietDown` (0x11734,
  the callee at 0x136b8) tests the same bit. Established; the name of bit 31 is the public one, the mask is read
  from the code.
- **0x4018** in `fglrx.o`: the public `GB_TILE_CONFIG` (exact). `fglrx_attach` at 0xbdc stores 23 (0x17) to it
  twice, before and after another store; in `r300_reg.h` that value is the enable bit, the R300 pipe count
  (3 << 1) and the 16-pixel tile size (1 << 4). Established. AMD's R3xx 3D register reference (page 30) agrees: ENABLE is bit 0, PIPE_COUNT bits 3:1 (3 is R300, 0 is RV350) and TILE_SIZE bits 5:4 (1 is 16 pixels).

Inferred from the Mesa comment and the two references.

## Bit layouts

This section records the bit layouts of the registers the shipped kernel object and X module reach, where a layout
can be stated. [VOYAGER_DECODE.h](../VOYAGER_DECODE.h) carries the same layouts in the shared decode-header form, and
`retools/tools/defs/check-publish-safe.py --config defs.toml` checks the header against this section row by row, so
a change to either side fails the check until the other follows.

Review status: written by the author of the decode header; the independent evidence review this repository's
datasheet process asks for has not happened, so nothing here is cleared yet.

How the layouts were derived and graded:

- Bit positions and names come from the public Linux radeon headers (`r100d.h`, `r300d.h`, `radeon_reg.h`,
  `r300_reg.h`) and Mesa's `r300_reg.h`, at the pins of the `linux/` and `mesa/` submodules. These describe public
  chips. They show what a public R3xx does, not what this board does.
- The shipped objects were then read at the sites listed in the sections above. Where the code touches a bit and the
  mask or value it uses agrees with the public layout, the field is **established**. Where only the public layout
  describes a field, it is **inferred**. Fields that neither source describes are not listed, and are called out as
  unknown below.
- Every register here is a 32-bit word in the 64 KB register aperture. Reset values were not observed: every
  register is **unknown** at reset. Access directions are those the code uses, widened to read-write for control
  registers the public headers treat as read-write.
- The grade on a register line in the header is the grade of the name bound to the offset, not of the access. The
  access (the shipped code reads or writes the offset) is established in the sections above for every register
  listed. A register line is **established** only where the AMD R3xx register guide, which is for this chip family,
  gives the same name, offset and layout: `GB_TILE_CONFIG`, `GA_SOFT_RESET` and `VAP_CNTL_STATUS` (checked against
  the guide's entries for 0x4018, 0x429c and 0x2140). Every other register line is **inferred**: the name comes from
  public headers of other chips, or from the offset alone.
- The 0x294 word has no public name. The block name `unnamed_0294` is a label chosen here.
- Where `r100d.h` and `r300d.h` disagree on a bit name (bit 2 of the soft-reset and bit 20 of the engine status are
  the older chips' setup-engine bits and the R300's vertex-engine bits), the field is named for the position
  (`geometry`) and graded inferred.

### Test values

Four values that this page already records are decoded by the header and checked against it: 0x17 written to
`gb_tile_config` at attach (enable, three pipes in the pipe-count field, 16-pixel tiles), 0x79 written to
`rbbm_soft_reset` by the engine reset (the CP, RE, PP, E2 and RB resets), 0x3000 as the stereo pair of
`unnamed_0294`, and 0x120000 as the pair of bits the kernel stereo routine ORs into `crtc_offset_cntl` (bit 17 and bit 20).

### What is still unknown, and what would settle it

- **Reset values of every register.** No capture of a board at reset was read. A register dump on a powered board
  before the driver attaches, or the vendor reference for the same chip, would settle them.
- **Meaning of bits `board_probe` (0x28 bit 13) and `board_strap` (0xe4 bit 27).** The kernel object tests them to
  mark a workstation board; no public header defines them. A reference guide for this exact chip or a board with the
  bit forced would settle them. The later M56 guide defines no such bits.
- **Meaning of `stereo_sel` and `mode_nibble` in 0x294, and of `stereo_aux` (0x228 bit 20).** Both objects move the pair
  together with the stereo switch, which says they relate to stereo, not what each value selects. Tracing the
  arguments of the X module's transmitter routine to their callers, or a reference for the compositor stage, would
  settle them.
- **Bit 14 of `dac_cntl`.** The gamma routine clears it; no public header names it. A chip reference would settle it.
- **Whether the older-chip and R300 names for the same bit (setup engine, vertex engine) apply to this part.** They
  differ in the public headers. The chip identity in the driver record, once traced, or the part's own reference
  would settle it.
- **`soft_reset_count` width.** Taken from Mesa's comment and AMD's R3xx reference, not from a write the code makes
  beyond the value 1024.
- **Pipe-count values other than 3** (`rv300`, `r420`) and **tile sizes other than 16** are inferred from the public
  headers; the code writes only 0x17.

## Not in the tables

- **The compositor I2C engine, 0x2e0, 0x2e4 and 0x2e8.** `fglrxCompositorI2cRegRead` at 0x5738 reaches them
  through the dword accessors by indexes 184 to 186, with the aperture loaded from board record +656 at 0x57a4. The
  replay does not resolve calls made through addresses built with `dsll32` and `dadd`, so these rows are absent
  from `mmio.tsv`. `radeon_reg.h` names the three `DVI_I2C_CNTL_0`, `DVI_I2C_CNTL_1` and `DVI_I2C_DATA`
  (and, at the same offsets, `DDA_CONFIG`, `DDA_ON_OFF` and `VGA_DDA_CONFIG`; the I2C names fit the code). The
  routine writes the first as (old value AND 0xfbff) OR 0x0aff0327, the second as (old value AND 0xffffff80) OR
  0xff020011, then sets bit 12 of the first and polls its bits 2:0 up to ten times, calling a helper with 2000
  between polls. That layout is the one `radeon_reg.h` gives the
  multimedia I2C registers at 0x90 and 0x94: bits 0, 1 and 2 are done, nack and halt, bit 12 is go, and the
  second word carries a data count, an address count and the enable at bit 17. Inferred, from the layout match.
- **0xf18.** `firegl_addmap` at 0x1bc50 reads the word at 0xf18 of the aperture right after storing its
  address at device record +1000, keeps the high half and stores it at device record +1008. `radeon_reg.h` lists
  0xf18 as `REG_BASE` in the PCI configuration space, which is another address space. Role not decoded. Unknown: the
  read, its location and the high-half keep are established from the disassembly of that routine; the register's meaning is
  not. Next route: find where device record +1008 is used later (the aperture map size or bus address), and search the
  AMD references and the Linux and X.Org tables for offset 0xf18 in the aperture. No REG line until it is named.
- **Calls through the accessor table.** No routine of `fglrx.o` calls `FGLRXReadRegister`,
  `FGLRXWriteRegister`, `FGLRXWriteRegister8` or `FGLRXINPLL` (see above), so the offsets their callers use are
  outside the objects read here.
- **Pointers derived from the aperture.** `firegl_addmap` also stores the aperture plus 0x40 at device record
  +400 and the aperture plus 0x898 at device record +992. Loads through those fields are not resolved.
- **Unresolved sites.** The replay found accesses through a base it knows but with an offset it could not
  trace; `inventory/summary.tsv` counts them. The X module's routines that take the aperture as a parameter other
  than the two PLL helpers are among them.
- **Base rules match by field offset.** The replay takes any 32-bit load at +48 in `fglrx_drv.so` (and any
  64-bit load at +656 or +1000 in `fglrx.o`) as the aperture base, so a load of another record's field at the same
  displacement would also yield rows. 177 of the 197 offsets in the X module have a public register name (exact,
  common, or a lane of one), which a stray structure field would rarely do; the 9 conflicts and 11 offsets with no
  name are the ones to read first.
- **Aperture size.** The window in the config is 0x10000 bytes, the size of the register BAR the public
  drivers use. An access beyond it is dropped, not counted.
- **Static routines.** The X module's symbol table names only 177 routines; code between two names is read as
  one extent. The row text `static code at ADDR` names such a routine by its start address. Each lies inside the
  extent of the symbol before it: 0x40ac40 in `R200EngineInit`, 0x40d200 in `R200AccelInit`,
  0x40eb00 in `R200DGAInit`, 0x410ec0 in `R200WaitForVerticalSync`, 0x4112c0 in `R200MinBits`, 0x4195c0 in
  `R200PreInit`, 0x41bc00 in `R200ScreenInit`, 0x42eb00 in `vRC6ProgramHTOT_CNTL_EDGE`, 0x437c3c in
  `miRegionBreak`, 0x43d100 in `FIREGL_OverlayCollectUnderlayRegions` and 0x43f4c0 in `QBS_EnableStereo`.

Everything this page leaves open is in [open-questions.md](open-questions.md), under "Register accesses".

## Specification registers of the R3xx 3D block

These are the 207 registers of the R3xx 3D block listed in the AMD *Radeon R3xx 3D Register Reference Guide*,
revision 1.0 (25 February 2008, the document named in [sources/INDEX.md](sources/INDEX.md)). The table in
[inventory/spec-registers.tsv](inventory/spec-registers.tsv) takes its rows from that guide's register headers
(the `scripts/inventory-config.json` `spec_registers` block), so the names and page numbers here are the guide's.
The field layouts come from the guide's field tables, read from its text layer; the guide's page numbers are the
printed ones.

Each entry gives the register's role and its fields in the guide's bit ranges. `r300_reg.h` is the Linux radeon
header at the pin in [sources/INDEX.md](sources/INDEX.md) (`linux/`, commit d89e1d18), read from the upstream file
at that commit. Where that header names the same offset with a different register, the entry says so, and the
guide's name is the one used. Where the header has no name for an offset, the entry says so too.

A register whose guide entry gives only a 32-bit data field, with no meaning beyond the name, is marked unknown in
its entry. No public source here describes what those registers hold. Settling them needs a fuller reference for
this chip or a test on the chip itself; the guide and the Linux header give no more.

The roles here are the guide's and the Linux header's. The voyager driver and kernel object are not a source for
the roles. An entry that cites a packet site uses it only to show that the register is programmed, and its
grade rests on that too.

### Colour buffer (CB)

- **0x4e00** `RB3D_CCTL` (R3xx p. 12; `r300_reg.h` none): unpipelined control. `NUM_MULTIWRITES` in bits 6:5 writes a quad to one to four buffers, `CLRCMP_FLIPE_ENABLE` in bit 7 turns on the flipped colour compare, `AA_COMPRESSION_ENABLE` in bit 9 turns on antialias colour compression, and bit 10 is reserved and written as zero. Linux v6.6 names no register at this offset. Observed: `__R300ReadPixels_UseLockUpload` in `fglrx_dri.so` at 0x8271f4 stores header 0x1380 and the constant 0 at 0x8271f8: one buffer, flip and compression off. Established.
- **0x4e04** `RB3D_BLENDCNTL` (R3xx p. 8; `r300_reg.h` `R300_RB3D_CBLEND`): colour blend control. `ALPHA_BLEND_ENABLE` is bit 0, `SEPARATE_ALPHA_ENABLE` bit 1 selects `RB3D_ABLENDCNTL` for alpha, `READ_ENABLE` bit 2 lets blending read the destination, `DISCARD_SRC_PIXELS` bits 5:3, `COMB_FCN` bits 14:12, `SRCBLEND` bits 21:16 and `DESTBLEND` bits 29:24. The guide's factor codes run from 1 to 13, with 14 to 31 reserved. Observed: `__R300NoGCSetOverrideRendering` in `fglrx_dri.so` at 0x76d74c stores header 0x1381 and the constant 0x20200000 at 0x76d754, so both factors are 0x20 with blending off. v6.6 names 0x20 `R300_BLEND_GL_ZERO`, and the guide's table has no entry for 0x20. Inferred.
- **0x4e08** `RB3D_ABLENDCNTL` (R3xx p. 5; `r300_reg.h` `R300_RB3D_ABLEND`): the blend-function fields for the alpha channel, used when `SEPARATE_ALPHA_ENABLE` is set: `COMB_FCN` bits 14:12, `SRCBLEND` bits 21:16 and `DESTBLEND` bits 29:24. Observed: `__R300LoadContext` in `fglrx_dri.so` at 0x787614 stores one header that covers this register and `RB3D_BLENDCNTL` (count 2, 0x11381); the word for 0x4e08 is loaded from the context at +291032, so the site gives no value. Inferred.
- **0x4e0c** `RB3D_COLOR_CHANNEL_MASK` (R3xx p. 14; `r300_reg.h` `R300_RB3D_COLORMASK`): one write enable per channel, blue in bit 0, green bit 1, red bit 2 and alpha bit 3, all defaulting to 1. With every channel of the current format off, the colour buffer discards every quad. Established.
- **0x4e10** `RB3D_CONSTANT_COLOR` (R3xx p. 15; `r300_reg.h` `R300_RB3D_BLEND_COLOR`): the constant colour the blender uses, one byte each: blue 7:0, green 15:8, red 23:16 and alpha 31:24. Observed: `__R300LoadContext` in `fglrx_dri.so` at 0x78762c stores header 0x1384 and then a context word at +291036; `__R300UpdateHWState` at 0x781b20 does the same. Inferred.
- **0x4e14** `RB3D_COLOR_CLEAR_VALUE` (R3xx p. 15; `r300_reg.h` none): the clear colour written when the colour mask is 00, in the same byte layout as the constant colour (blue 7:0 through alpha 31:24). Linux v6.6 names no register at this offset. Observed: `__R300ClearCMask` in `fglrx_dri.so` at 0x760494 stores header 0x1385 and then a context word at +291040, so the site gives no value. Inferred.
- **0x4e18** `RB3D_ROPCNTL` (R3xx p. 16; `r300_reg.h` none): `ROP_ENABLE` is bit 2, and with it clear the ROP is forced to code 0xC. `ROP` in bits 11:8 is the GDI ROP2 code, which is replicated into two nibbles to form the ROP3 code. Linux v6.6 names no register at this offset. Observed: `__R300CompleteOverrideRendering` in `fglrx_dri.so` at 0x76faa4 stores header 0x1386 and then a context word at +291148; no constant is read. Inferred.
- **0x4e1c** `RB3D_CLRCMP_FLIPE` (R3xx p. 13; `r300_reg.h` none): the flipped colour-compare value, all 32 bits, kept apart from the 2D register. Linux v6.6 names no register at this offset. No driver site in the inventory. Inferred.
- **0x4e20** `RB3D_CLRCMP_CLR` (R3xx p. 12; `r300_reg.h` none): the colour-compare colour, all 32 bits, kept apart from the 2D register. Linux v6.6 names no register at this offset. No driver site in the inventory. Inferred.
- **0x4e24** `RB3D_CLRCMP_MSK` (R3xx p. 13; `r300_reg.h` none): the colour-compare mask, all 32 bits, kept apart from the 2D register. Linux v6.6 names no register at this offset. No driver site in the inventory. Inferred.
- **0x4e28** `RB3D_COLOROFFSET[0-3]` (R3xx p. 13; `r300_reg.h` `R300_RB3D_COLOROFFSET0`): base address of each of four multibuffer targets, bits 31:5, 256-bit aligned. The cache must be empty before a change. Established.
- **0x4e38** `RB3D_COLORPITCH[0-3]` (R3xx p. 13; `r300_reg.h` `R300_RB3D_COLORPITCH0`): `COLORPITCH` bits 13:1 in units of two pixels, `COLORTILE` bit 16 for macro tiling, `COLORMICROTILE` bits 18:17, `COLORENDIAN` bits 20:19 and `COLORFORMAT` bits 24:21 (default 6, ARGB8888). v6.6 puts the pitch mask at bits 12:3, the endian field at bit 18 and the format field at bit 22, and its own comments mark those names provisional. Observed: `__R300HWBlt_SetupPitchAndOffset` in `fglrx_dri.so` at 0x76e3c8 stores header 0x138e and then a word built from the routine's arguments, so no constant is read. The four-register packet header at 0x82331c in `__R300DrawPixelsBlt` also covers this offset.
  Targets 1 to 3 at 0x4e3c, 0x4e40 and 0x4e44 have the same fields. Observed: `__R300HWBlt_SetupPitchAndOffset` stores headers 0x138f, 0x1390 and 0x1391 at 0x76e3bc, 0x76e3d4 and 0x76e3ec, each followed by a word built from the arguments. v6.6 names them `R300_RB3D_COLORPITCH1` to `R300_RB3D_COLORPITCH3` and marks those names provisional too. The packet at 0x82331c covers them as well. Inferred.
- **0x4e4c** `RB3D_DSTCACHE_CTLSTAT` (R3xx p. 15; `r300_reg.h` none): `DC_FLUSH` in bits 1:0 writes dirty 3D data out (2 or 3), `DC_FREE` in bits 3:2 invalidates the 3D tags (2 or 3), and `DC_FINISH` bit 4 sends a finish signal to the command processor. v6.6 has a comment that the register is set to 0x0a before 3D operations and to 0x02 afterwards. Observed: `CopyToSystem` in `fglrx_dri.so` at 0x86e410 stores header 0x1393 and then 3 at 0x86e450 (flush only); `__R300FlushCaches` at 0x8bd544 stores 2 at 0x8bd54c; `__R300ReadPixels_UseLockUpload` at 0x82716c and `__R300ClearCMask` at 0x760484 store 0x0a. Established.
- **0x4e50** `RB3D_DITHER_CTL` (R3xx p. 15; `r300_reg.h` none): `DITHER_MODE` in bits 1:0 picks truncate (0), round (1) or lookup-table dither (2) for colour, and `ALPHA_DITHER_MODE` in bits 3:2 uses the same codes for alpha. Linux v6.6 names no register at this offset. Observed: `__R300LoadContext` in `fglrx_dri.so` at 0x786fa0 stores header 0x1394 and then a context word at +291140; no constant is read. Inferred.
- **0x4e80** `RB3D_AARESOLVE_OFFSET` (R3xx p. 5; `r300_reg.h` `R300_RB3D_AARESOLVE_OFFSET`): the resolve destination address, bits 31:5, 256-bit aligned. Established.
- **0x4e84** `RB3D_AARESOLVE_PITCH` (R3xx p. 5; `r300_reg.h` `R300_RB3D_AARESOLVE_PITCH`): the resolve destination pitch in bits 13:1, in units of two pixels, with its tiling control. Established.
- **0x4e88** `RB3D_AARESOLVE_CTL` (R3xx p. 5; `r300_reg.h` `R300_RB3D_AARESOLVE_CTL`): `AARESOLVE_MODE` bit 0 sets resolve (1) or normal (0) operation, and `AARESOLVE_GAMMA` bit 1 picks a 1.0 or 2.2 gamma for the samples before and after filtering. v6.6 names the register only. Observed: `__R300LoadContext` in `fglrx_dri.so` at 0x787190 stores header 0x13a2 and then a context word at +294000; `__R300ResolveMultisampledColorBuffer` at 0x762000 stores the same header with a computed word. No constant is read. Inferred.

### Fog and fragment-stage fog (FG)

- **0x4bc0** `FG_FOG_BLEND` (R3xx p. 18; `r300_reg.h` `R300_RE_FOG_STATE`): `ENABLE` is bit 0 (0 passes the input colour through), and `FN` in bits 2:1 picks linear (0), exponential (1), exponential squared (2) or the constant fog factor (3). The `R300_FOG_MODE_*` values in v6.6 match. Established.
- **0x4bc4** `FG_FOG_FACTOR` (R3xx p. 18; `r300_reg.h` none): the constant fog factor, `FACTOR` in bits 9:0 as a (0.9) fixed-point value. Linux v6.6 names no register at this offset. Observed: `__R300DrawPixelsBlt` in `fglrx_dri.so` at 0x822e18 stores header 0x12f1, then the converted fog factor masked with 0x3ff at 0x822e20, which matches the ten-bit field. Established.
- **0x4bc8** `FG_FOG_COLOR_R` (R3xx p. 18; `r300_reg.h` `R300_FOG_COLOR_R`): the red component of the fog colour, bits 9:0, (0.9) fixed point. Established.

- **0x4bd0** `FG_FOG_COLOR_B` (R3xx p. 18; `r300_reg.h` `R300_FOG_COLOR_B`): the blue component of the fog colour, bits 9:0, (0.9) fixed point. Established.

- **0x4bd8** `FG_DEPTH_SRC` (R3xx p. 17; `r300_reg.h` none): `DEPTH_SRC` bit 0 picks where depth comes from, the scan converter's plane equation (0) or the shader's four discrete values (1).
