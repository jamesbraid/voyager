# Option ROM images

The three video option ROM images of the IRIX 6.5.30 Onyx4 install: `sg2.bin` (FireGL X1, R300), `sg3.bin` and `sg3a.bin` (FireGL X2, R350). All offsets are byte offsets into the image. `scripts/option_rom.py` reproduces every table below from the images alone (`dump`, `walk`, `diff`).

Labels: **established** (read in the image, or in the whole body of a routine), **inferred** (a reading, with its reasoning), **unknown**. The layouts come from public sources, so a decoded meaning is a cross-check from the public chips, not proof of what the board or the IRIX driver does: the PCI Local Bus Specification's expansion ROM structures as written in EDK2 `Pci22.h`, the Linux radeon driver's `radeon_combios.c` and `radeon_bios.c` (the ATI table header and tables), and Linux `uapi/video/uvesafb.h` (the VESA information block); see [sources/INDEX.md](sources/INDEX.md). No part of an image is copied into this repository.

## The three images

**established.** Every image is 40960 bytes (80 sectors of 512), the byte sum of the whole file is 0 modulo 256, bytes 0x55 0xaa open it, and the last 3 KB or so are 0xff padding (content ends at 0x938e in sg2, 0x969e in sg3 and 0x968e in sg3a).

- **established.** All three carry the string ` 761295520` at 0x30 and the copyright line `(C) 1988-2003, ATI Technologies Inc.` followed by the version string, at 0xb8 (sg2), 0xb9 (sg3) and 0xa9 (sg3a). The version string has the form `VERaaa.bbb.ccc.ddd`; the flash tool reads it with `sscanf("VER%d.%d.%d.%d")` (below), giving 1.114.39.1, 1.110.39.0 and 201.211.39.0.
- **established.** The title carries a part number in sg2 (113-99002-114) and sg3 (113-A10503-110) and none in sg3a. The strings name the boards "256p": 256 MB, matching the memory size the tables give (below), is an **inferred** reading of "256".
- **established.** The product string names the board "AGP" in all three images. Whether the Onyx4 boards attach by AGP, PCI or PCI-X is **unknown**; see `open-questions.md`.

## PCI expansion ROM structure

- **established.** Offset 0x18 holds a 16-bit pointer to the PCI data structure: 0x194, 0x194, 0x184. The structure reads, field by field as in `Pci22.h`: signature `PCIR`; vendor 0x1002; device 0x4e47 (sg2) or 0x4e4b (sg3, sg3a); device-list pointer 0; length 0x18; revision 0; class code bytes `00 00 03` (programming interface 0, subclass 0, base class 3, a VGA-compatible display controller); image length 0x50 sectors; code revision 0x0172 (sg2), 0x016e (sg3), 0xc9d3 (sg3a); code type 0; indicator 0x80.
- **established.** `file(1)` reports "ProgIF=3" for these images. It reads the class code in the wrong order; the base class is 3 and the programming interface is 0.
- **established.** Code type 0 is the x86 PC-AT image type (`PCI_CODE_TYPE_PCAT_IMAGE` in `Pci22.h`). Each image holds this one image and no other: indicator bit 7 (last image) is set, the image length equals the file length, and `PCIR` occurs once. No Open Firmware (FCode) image and no EFI image is present in any of the three.
- **established.** The 3-byte init entry at offset 3 is a near jump (`e9`, 16-bit displacement): sg2 jumps to 0x6c8, sg3 to 0x6d3, sg3a to 0x6c3. The stub saves the registers, calls the PCI BIOS function through `int 0x1a` (ax = 0xb109 and 0xb10c), writes through I/O ports at an offset of 0x14, 0x16 and 0x2e from a base it read, and falls into the card's set-up. It uses 16-bit real-mode instructions throughout (the images disassemble as 16-bit x86 and contain `pushad`/`popad` forms with the operand-size prefix). The whole init path is read in [BIOS code](#bios-code).
- **established.** The code writes into its own image: it stores 0x1234 at 0x634a (sg2) and switches to a stack that ends at 0x6552 only if the word reads back as 0x1234. The image holds 0x3412 there, so from a ROM mapping the store is lost, the test fails and the caller's stack stays; from a RAM copy the stack moves into the zero-filled run of 0x206 bytes that starts at 0x634c (sg3 and sg3a have the same run, 0x207 bytes long, at 0x665b and 0x664b) and is switched back at exit. The scratch use of the hole is **inferred**. The host side does shadow the image; see the section on the IRIX software. [BIOS code](#bios-code) has the sequence.

## ATI table header

**established.** The 16-bit word at 0x48 points to the ATI table header (0x128, 0x128, 0x118). It is not an ATOM BIOS: the four bytes at header+4 are not `ATOM` or `MOTA` (they are the second revision word and the length, see below), and neither string occurs anywhere in any of the three images (a search of the whole file for both returns nothing). **established.** There is therefore no ATOM command table or data table for an ATOM disassembler such as AtomDis to read; the register scripts the BIOS runs are the legacy tables this chapter decodes, and `scripts/option_rom.py walk` prints them. The images are the older table-driven kind that the Linux radeon driver reads as a "COMBIOS", the form of the R300 and R350 era. The header is 0x6a bytes long (the byte at header+6, which Linux also reads as the length) and ends two bytes before the PCI data structure.

Fields:

- **established.** header+0x00: 0xa008 in all three. Unknown purpose.
- **established.** header+0x02 and +0x04 (two words, stored high byte first, unlike every other field of the header and the PCI data structure, which are little-endian): 0x0172 and 0x0172 (sg2, bytes `01 72 01 72`), 0x016e and 0x016e (sg3), 0x010a and 0xc9d3 (sg3a, bytes `01 0a c9 d3`). Read that way the second word equals the PCI data structure's code revision (little-endian there) in each image. What the first word means: **unknown**.
- **established.** header+0x08 and +0x0a: pointers (0x1c73, 0x56e6), (0x1c4b, 0x56be), (0x1c3b, 0x56ae). The second points at the `PMID` block in each image. The first points into code (bytes `fc 80 fc a0 0f 84 ...`): **established** as the second byte of the video interrupt handler, the `cld` after `sti` ([BIOS code](#the-video-entry-and-its-tables)); the slot is the handler address plus one.
- **established.** header+0x10 points at the build tag, header+0x12 at the line break before the title string (0x80), header+0x14 at the product string (0x10b, 0x10c, 0xfc). The public driver names the slot at +0x14 the "BIOS support" table; here it holds the product string.
- **established.** header+0x18 and +0x1a: 0xc000 and 0xf000. **inferred**: real-mode segments (the legacy video ROM segment and the system BIOS segment).
- **established.** header+0x1c, +0x1e and +0x20 are 0x1002, 0x0152 and the device ID (0x4e47 or 0x4e4b), the same in the PCI data structure's device field. **inferred.** The first two form a vendor and device pair, 1002:0152, that matches the second word of the entries for 4e47 and 4e4b in the kernel driver's ID tables, which have the form of a subsystem vendor and device pair ([kernel-attach.md](kernel-attach.md#which-cards-the-driver-claims)). So the ROM would state the subsystem ID of both boards as 1002:0152. Nothing reads that pair, so this is a match of values only.
- **established.** header+0x0e points to a block (0x1bf, 0x1bf, 0x1af) of a 32-bit value, four bytes of 0xff, a 16-bit value and two more bytes, then four bytes of 0xff, repeated 0x20 bytes later: 0xd5a899e7 and 0x026a (sg2), 0x61f25c69 and 0xb003 (sg3), 0x5691f6e8 and 0xb73a (sg3a). The first copy in sg2 has 0x0201 in the two extra bytes; every other copy has 0. The values differ in every image and look like per-image signature words. **unknown.**

## Tables decoded

All of these follow the public driver's layout (`radeon_combios.c`); every number below was read from the image.

### PLL info (slot +0x30)

- **established.** Revision byte 10, length byte 70. Reference clock word 2700, reference divider 12, pixel-PLL output range 20000 to 40000 and input range 40 to 3000 (+0x36 and +0x3a), system-PLL and memory-PLL reference divider 4 and output range 30000 to 80000. These are the same in all three.
- **established.** The default system clock word (+0x0a) and memory clock word (+0x08): 32400 and 27600 (sg2); 37800 and 31700 (sg3 and sg3a).
- **inferred.** The public driver's units are 10 kHz. That gives a 27.00 MHz reference clock, a 200 to 400 MHz pixel-PLL output range, and default clocks of 324 MHz system and 276 MHz memory (X1) and 378 MHz and 317 MHz (X2). The two X2 images agree.
- **established.** The public driver reads the system-PLL and memory-PLL input ranges only for revisions above 10, so it does not read those fields here; the bytes after +0x46 are not part of the table (the next block is code).

### Memory size (slots +0x5e and +0x48)

- **established.** The misc info table (revision 1) points at the detected-memory table (0x20c, 0x20c, 0x1fc). It reads: revision 0, a 32-bit word 0x2a, a 16-bit size of 256. The memory config table has revision byte 1 and its first byte is 0x80 (128).
- **inferred.** The public driver reads the first as 256 MB, and would read the second (used only when the first is absent) as 128 doubled, 256 MB: the two agree in all three images, so each board is a 256 MB card, matching "256p" in the names.

### Connector info (slot +0x50)

- **established.** The same four bytes in all three: a header word 0x1211, then two entries 0x3300 and 0x3211, then 0x0000.
- **inferred.** The public driver reads each entry as: connector type in bits 15:12 (3 = DVI-I), DDC line in 11:8, bit 4 = second digital output (the external-transmitter path), bit 0 = second analogue DAC. Entry 0x3300 is a DVI-I connector with DDC line 3 (VGA line), first DAC, internal TMDS. Entry 0x3211 is a DVI-I connector with DDC line 2 (DVI line), second DAC, external TMDS. That is two DVI-I outputs, which fits a two-head board; the IRIX driver's own reading is **unknown** (`fglrx_drv.so` prints "Connector Layout from BIOS", not read).
- **established.** The X1 image has the connector entries but no external TMDS table (below).

### External TMDS info (slot +0x58, sg3 and sg3a only)

- **established.** Revision byte 2, length byte 27, an 8-bit slave address byte 0x70 at +6, a DDC code byte 4 at +7, a flags byte 0x80 at +9, then a script from +10 to a 0xffff terminator: five two-byte ids of type 6 (a byte written to a register of the transmitter over I2C) with register and value pairs 0x08 / 0x39, 0x0a / 0xf0, 0x0c / 0x89, 0x09 / 0x20, 0x0d / 0x90. 10 + 5 x 3 + 2 = 27 bytes, so the length byte covers the whole table. The two images carry identical tables.
- **inferred.** The 0x70 address is the 8-bit form of a 7-bit address 0x38. The part is **unknown**; the public driver hard-codes the same address for one transmitter family on integrated chipsets, which is not evidence for this board.

### ASIC init, memory-controller and clock scripts

- **established.** The two ASIC init tables, the two misc-info tables (ASIC init 3 is empty), the PLL init table and the dynamic clock table all walk to their zero terminators with the public driver's decoding, and each ends within one byte of where the next table starts, so the boundaries are consistent. Counts of entries:

| Table | sg2 | sg3 | sg3a |
|---|---|---|---|
| ASIC init 1 | 46 | 47 | 47 |
| ASIC init 2 | 33 | 33 | 33 |
| ASIC init 3 | 0 | 0 | 0 |
| ASIC init 4 | 25 | 25 | 25 |
| PLL init | 64 | 65 | 65 |
| dynamic clock 1 | 9 | 9 | 9 |

- **inferred.** The MMIO tables write registers by offset; in the public headers the offsets used most are the indirect memory-controller index and data pair (0x1f8 and 0x1fc, in the R300 header) and the memory timing, framebuffer location, latency-timer and SDRAM mode registers at 0x140 to 0x158. The remaining offsets include bus control (0x30), CRTC and DAC control (0x50, 0x58, 0x7c), GPIO pad registers (0x198 to 0x1a0), display output (0xd00 to 0xd64) and the graphics buffer controls (0x2f0, 0x3f0). The names are the public header's; this chapter has not checked each against AMD's register reference.

## Tables the public driver does not read

Five slots of the ATI table header name tables that the public driver does not decode: DAC programming (+0x2a),
maximum colour depth (+0x2c), CRTC info (+0x2e), hardware config (+0x36) and save mask (+0x4a). The pinned trees have
no reader for them. Linux v6.12 `drivers/gpu/drm/radeon/radeon_combios.c` (fetched for this check) lists each slot
in its table enum and its offset switch, and nothing else in the file reads the tables. Offsets are sg2's; sg3 and
sg3a follow in the last paragraph.

**established.** A search of each image for `ATOM` and `MOTA` finds nothing, and the word at header+4 is the
revision word, not a magic value. An AtomDis run therefore has no input in these images. The tables below are in
the older table format.

- **hardware config (0x6b6).** **established.** Ten bytes: `$ATI`, then `02 0a 0f 00 00 02`. The connector table
  begins at +10 in all three images. **inferred:** the pair `02 0a` is a revision and a length, the way the other
  tables start. The last four bytes (`0f 00 00 02`) and the table's role are **unknown**. The table holds no
  register script.
- **DAC programming (0x6f40).** **established.** The first 28 bytes are `80 20 20 01 01 01 01 01 20 00 00 01 20 ff`,
  eight `de` bytes, then `7f fe ff fe b4 0a`. At +28 (0x6f5c) the bytes `be 40 6f` load si with the table's own
  address, and 16-bit code follows: an index through `ah`, a near call, then a byte written with 0xff and a byte read
  through dl = 0x5b and 0x59. The code sets only dl, so the port's high byte comes from dh, which this sequence
  does not set. So the block is partly code, its end is not known, and the routine that runs it is not read. Role **unknown**. The sg3 and sg3a copies load their own addresses,
  0x7250 and 0x7240.
- **maximum colour depth (0x661c).** **established.** Seven-byte records, the same in all three images for the first
  16 bytes. The first records are `40 00 80 03 4b 00 06`, `50 00 80 03 5a 00 06`, `64 00 80 06 96 00 06`,
  `64 00 80 04 96 00 05`, `64 00 80 03 96 00 04` and `80 00 80 09 dc 00 06`, and the records run past 0x667e. The
  first word is 64, 80, 100, 128, 144 or 160 in the records read here. **inferred:** that word is a width in units
  of 8 pixels (512, 640, 800, 1024, 1152 and 1280 pixels), and the last byte is a colour-depth code (2, 4, 5 or 6
  in these records). The second word (896 to 3712, always a multiple of 128), the third (75 to 245) and the 0x82
  flag in one record are **unknown**. The table writes no registers.
- **CRTC info (0xd23).** **established.** Twenty-byte records. The first three begin with the index bytes e2, e3 and
  e4; the bytes at +60 do not start another record of that kind. The fields inside the record are **unknown**. This
  table is not decoded beyond the record boundary.
- **save mask (0x75df).** **established.** The block is 36 bytes: `08 1f 00 58 f0 01 68 00 03 6c 00 03 e2 0f 00 00 42 70 00 00 1a 00 80 26 00 40 2a 10 40 4c ff ff 4e 1f 00 00`.
  From 0x7603 the bytes are code (`push cx`, `push dx`, `push bx`, a near call), so the table is at most 36 bytes. Its
  layout as 32-bit words is **unknown**.

sg3 and sg3a: the hardware config table is the same ten bytes, and the first 16 bytes of the maximum colour depth
table and the first records of the CRTC info table match sg2. The save mask block is the same 36 bytes in all
three. The DAC programming block differs only in its own address, as above. The records and blocks are the same
size in each image.

## VESA and protected-mode blocks

- **established.** The image holds a VESA information block template (at 0x4ae4, 0x4abc and 0x4aac) whose fields match the layout of `struct vbe_ib` in `uvesafb.h`: signature `VESA`, version 0x0200, the OEM string pointer (0x1ac, 0x1ac, 0x19c, which does point at the OEM string), capabilities 1, a mode list pointer (0x486e, 0x4846, 0x4836), total memory 0 (filled at run time), software revision 0x0100, and pointers to the vendor name `ATI Technologies Inc.`, the product name (`FireGL X1-256p` or `FireGL X2-256p`) and the product revision `01.00`. All three pointers hit their strings in each image.
- **established.** The mode list holds 56 mode numbers ending in 0xffff, the same list in all three images: 0x6a, 0x102, 0x104, 0x182, 0x10d to 0x10f, 0x120, 0x192 to 0x196, 0x1a2 to 0x1a6, 0x1b2 to 0x1b6, 0x1c2 to 0x1c6, 0x100, 0x183 to 0x186, 0x101, 0x110 to 0x112, 0x121, 0x103, 0x113 to 0x115, 0x122, 0x105, 0x116 to 0x118, 0x123, 0x107, 0x119 to 0x11b, 0x124, 0x109, 0x10a, 0x130.
- **established.** A `PMID` block (the VESA protected-mode information block) sits at 0x56e6, 0x56be and 0x56ae with the standard selectors 0xa000, 0xb000, 0xb800 and 0xc000 after the entry and init offsets.
- **inferred.** An 8x16 character font table is in the image (one glyph checked): the glyph bytes `7e 81 a5 81 81 bd 99 81 81 7e` (a smiling face in the standard PC character set) occur once, at 0x2e39, 0x2e11 and 0x2e01.

## How the images differ

**established.** sg2 and sg3 are different boards, so the differences are table content. Beyond the identity strings and the device ID:

- The PLL info table gives different default clocks (above).
- sg3 has the external TMDS table; sg2 has none.
- The memory-controller scripts differ in values: the indirect registers at index 0x119, 0x11b, 0x11d and 0x11f are written 0x9999aaaa in sg2 and 0x9999555e in sg3; indexes 0x11a, 0x11c, 0x11e and 0x120 are written 0x141557ff in sg2 and 0x161557ff in sg3 (and the ASIC init 4 pass writes 0x151557ff and 0x171557ff); the memory timing register (0x144) is 0x1a292b13 in both, but the value ORed into the DAC macro control register (0xd04) is 0x808 in sg2 and 0xa0a in sg3; the first PLL-init write to index 10 holds 0x1302904 in sg2 and 0x1382f04 in sg3; and the dynamic clock table's write to index 45 holds 0xefc80 in sg2 and 0x771efcc0 in sg3 (sg3 also writes index 45 once more, in the PLL init table).
- ASIC init 1 has 46 entries in sg2 and 47 in sg3: sg3 writes 0x923def to register 0x188 and then ORs in 0x10000, where sg2 ORs in 0x923def in one step.
- The ASIC init 4 script clears bits 25:24 of indirect registers 0x11a, 0x11c, 0x11e and 0x120 twice in sg2; in sg3 and sg3a the second pass sets bit 25 instead.
- The CRT info table differs in two bytes (`88 78` against `aa 55`).

**established.** sg3a is sg3 with the title, version and part-number strings changed, a shorter string area (everything from the product string on moves down by 0x10 bytes) and a small number of content changes. After removing the 0x10-byte shift, `option_rom.py diff` leaves only the differences below over the compared range (0x19c to 0x9000, about 36 KB); the rest is identical apart from the pointers the shift moves. The two X2 images agree on the default clocks, the connector table, the external TMDS script and the DAC macro value.

| Where (sg3a offset) | sg3 | sg3a | What |
|---|---|---|---|
| 0x2fb to 0x30d | register 0x178 = 0x7020; 0x17c and index 0x124 of the indirect set = 0x0db30db3 | 0x4026; 0x39933993 | memory-controller read control values (ASIC init 1) |
| 0x362 to 0x388 | indexes 0x11a, 0x11c, 0x11e, 0x120 = 0x161557ff | 0x141551ff | four indirect-register writes |

| 0x595d to 0x5962, 0x71fb to 0x7200 | `push cx; mov cx,2; jmp` | `push bx; mov bx,2; jmp` | one small x86 helper, in two copies; the behaviour is unknown |

- **inferred.** The X2 changes are memory-controller and memory-timing values, which fits a retuned memory configuration, such as a different memory part or speed. That is a reading from the values; the registers' fields are not decoded here and no manual names a reason. The default clocks (317 MHz memory, 378 MHz system) are the same in both.
- **established.** The version string has a different leading field (001 in sg3, 201 in sg3a) and a later date (2005/04/06 against 2004/05/06). The flash tool's records (below) list `sg3a.bin` and `sg3b.bin` for the same PCI device as `sg3.bin`, and select between them by two bits on the card.

## BIOS code

The init entry and every routine it reaches were read as 16-bit x86 code (the call graph from the entry has 65 routines in `sg2.bin` and 72 in `sg3.bin` and `sg3a.bin`; far calls wrap inside the 64 KB segment, so `call 0x8b6d` at 0x7e6 reaches 0x9356). **established** means the whole body was read. Register names are the public names from X.Org `radeon_reg.h` (xf86-video-ati 6.14.6): a cross-check, not proof of what the board does. There is no ATOM table in these images (see above), so an ATOM disassembler has nothing to decode. The video entry's handlers (below) are located, not read, except entry 00 in part; the VBE and vendor handlers are read as listed there.

### How the chip's registers are reached

**established.** Nothing in the init path touches the chip through memory addresses. Every register access goes through the card's I/O BAR (configuration offset 0x14: the BAR the early console sets to I/O address 0x400, see [kernel-attach.md](kernel-attach.md)). Its base `P` is kept in `cs:[0x142]`. Three access forms occur:

- Indexed: write the register offset to `P+0` (the public `MM_INDEX`), then read or write the value at `P+4` (`MM_DATA`). The accessor saves the old index and writes it back afterwards. Whole dword: `5913` reads register bx, `586a` writes it. Single byte or word of the dword (lane in cl, 0 to 3): `5898` reads lane 0, `58a7` reads lane 3, `57f3`, `57f8` and `5802` write a byte to lane 0, 1 and 3, and `5835` writes a word to lane 0.
- Direct: the first 256 registers are used at `P+offset`, for example the BIOS scratch registers 0x10 to 0x2c, `BUS_CNTL` (0x30), `CRTC_GEN_CNTL` (0x50), `I2C_CNTL_0` (0x90). `5720` writes ax, `5727` reads al and `572e` reads ax at `P` plus the low byte of dx; `5735` forms that address.
- PLL: write 0x80 OR (index and 0x3f) to `P+8` (`CLOCK_CNTL_INDEX`), read or write the data at `P+0xc` (`CLOCK_CNTL_DATA`), then write 0 to `P+8`. Bits 7:6 of the index byte pick the byte lane of the PLL register (data port `P+0xc` plus the lane). `6869` is read-modify-write (ch is the AND mask, ah the OR value), `684a` reads a byte, `6a32` writes a dword.

`5743` returns dx = `P` (0 if none stored) after calling `5752`, which accepts the stored base when the word at `P+0x2e` equals the PCI data structure's device ID (word at 0x19a in sg2). Otherwise it reads configuration dword 0 (ports 0xcf8 and 0xcfc, `57d6`) of each device from the bus, device and function stored at `cs:[0x13e]` upward, one device at a time up to bus 8, until it equals the vendor-and-device dword at 0x198, then takes bits 15:8 of its BAR 1 as the base (low byte 0).

### The init entry (sg2 addresses; sg3 and sg3a in the table below)

- Entry `0x6c8`: **established.** Pushes all registers; the first time only (word `cs:[0x13e]` zero) it stores ax, which holds the card's PCI bus, device and function number, there and cs at `cs:[0x140]`. It reads configuration offset 0x14 with `int 0x1a` ax = 0xb109 (PCI BIOS read word), clears bits 1:0, and if the result is zero writes 0xf000 back (ax = 0xb10c, write word) so the I/O BAR gets an address. It stores the result at `cs:[0x142]`; the compare after the store tests the stored value against itself, so the branch back to 0x6eb is never taken. Then it writes three words through the I/O window: cs to `P+0x14`, the bus/device/function to `P+0x16` and the device ID from the PCI data structure to `P+0x2e`. Those are the halves of `BIOS_1_SCRATCH` (0x14) and the upper half of `BIOS_7_SCRATCH` (0x2c): the BIOS records where it runs and which card it serves. Next it stores 0x1234 at `cs:[0x634a]` and tests that it reads back (true only for a RAM copy); if so it saves ss, sp and ax at 0x634e, 0x6350 and 0x634c and sets ss:sp to cs:0x6552, the top of the zero-filled hole (**inferred**: scratch stack). The main sequence follows: `0x888`, ASIC init 1 (`6574` with bx = 0x2a7), `0x8b4`, `0x7d8`, `0x7c0`, the bridge fix below, `0x92d`. It then pops everything and, unless `cs:[0x634a]` already holds 0x3412, restores ss:sp and stores 0x3412 there; it returns far. In sg3 and sg3a the order is the same with one more call, the external-transmitter set-up (`5f7d` and `5f6d`), after `7a7` and `797` (their `0x7d8`) and before `78f` and `77f` (their `0x7c0`).
- Bridge fix (0x75d to 0x79a): **established.** Saves the PCI configuration address register (port 0xcf8), selects bus 0, device 1, function 0, offset 0 and reads the ID dword. When it is 0x25528086 (vendor 8086, device 2552, which the public PCI ID list names "E7505/E7205 PCI-to-AGP Bridge") it reads offset 0x70 of that function, sets bit 9 and writes it back. It restores the address register. What that bit does is **unknown**. On any other ID it changes nothing.
- `0x888`: **established.** Runs the three-word table at 0x890 through `6574`: write 0 to registers 0x20, 0x24, 0x28 and 0x2c (`BIOS_4_SCRATCH` to `BIOS_7_SCRATCH`), then AND 0xfffffffb and OR 4 on register 0x10 (`BIOS_0_SCRATCH`), which sets bit 2.
- `0x8b4`: **established.** Writes 5 to the VGA miscellaneous output register (port 0x3c2), reads ports 0x3da and 0x3ba, writes 0 to the attribute port 0x3c0 and 0x2001 to the sequencer port 0x3c4. With interrupts off it then sets real-mode vectors (offsets in sg2, segment cs unless noted): vector 0x42 to F000:F065, which is the system BIOS's own video handler, kept for chaining; vector 0x1f to 0x2a14; vector 0x43 to 0x2e27; vectors 0x10 and 0x6d both to 0x1c72; the word pair at linear 0x4a8 (the video save pointer) to 0x1ce6. When the `PMID` block's in-protected-mode word (0x56f8) is zero it first stores cs in the block's code-segment selector word (0x56f6), which every later use of ds for the ROM copy reads. It then stores that segment in three words of the table at 0x1ce6 (0x1ce8, 0x1cf8, 0x1d0a), the segment halves of its pointers. **inferred:** 0x2a14 and 0x2e27 are the 8x8 upper-half and 8x16 character tables (the 8x16 smiley glyph recorded above lies at 0x2e39). Vector 0x6d is the copy the ROM's own code calls.
- `0x7d8`: **established.** The main set-up: PLL init script (`6a49` with si = 0x58f), `6552`, `6b12`, `0x9356` (below), `7766`, the dynamic clock script (`6a49` with si = 0x661), `843`, `81f`, `0x92ac` and `0x9286` (below), `f99`, `5013`; then reads register 0x1c0 (public `SEPROM_CNTL1`), replaces bits 31:24 with 0x06 and writes it back.
- `0x7c0`: **established.** Prints the title line at 0x80 with the ROM's own video entry (`int 0x6d`, ax = 0x1301 write string, attribute 7, cursor from `[0x450]`): a count (cx) of 0x38 in sg2, 0x39 in sg3 and 0x29 in sg3a, which is the title with its line breaks plus the terminating zero byte (the visible text is 0x37, 0x38 and 0x28 bytes).
- `0x92d`: **established.** In RAM, limits the size byte at offset 2 to 0x80, clears the byte at 0x21, sums the first 0x8000 bytes and stores the two's complement at 0x21, then sums the next (size - 0x40) x 512 bytes and stores the two's complement in the byte before 0x9350 (0x934f in sg2, 0x965f in sg3, 0x964f in sg3a). It makes the image sum 0 again after the run changed bytes of it.
- `0x9356`: **established.** Sets bit 26 of `CRTC_GEN_CNTL` (the byte at `P+0x53`, bit 2: public `CRTC_DISP_REQ_EN_B`), writes 0x2a to lane 0 of register 0x140 (`MEM_CNTL`; the detected-memory table above holds 0x2a), writes the word 0x1000 to `P+0xfa`, the upper half of the dword at 0xf8 (public `CONFIG_MEMSIZE`), then clears bit 26 and sets bit 25 (`CRTC_EN`) and waits 15 times 2 ms (`59a1`). The 0x1000 is a literal, not a probed size; **inferred:** as the upper half of a byte count it reads 0x10000000, 256 MB, which agrees with the memory-size tables above.
- `0x92ac` and `0x9286`: **established.** `92ac` builds in bx a pair of display codes (one byte 7 or 8, the other 0, 1 or 2) from bit 1 of the byte at linear 0x489, bit 0 of the miscellaneous output register (port 0x3cc), whether a CRTC answers at port 0x3b4 or 0x3d4 (`7c49`) and the low byte of the CRTC base port in the BIOS data area (`78ce`). `9286` looks the pair up, as it is and then byte-swapped, in the words that start at 0x932e (the byte at 0x932a is the loop limit, 0x10, tested with a signed less-or-equal against the running index) and stores the index it finds, or 0xff, at linear 0x48a. **inferred:** the pair is the VGA display combination code of video function 1a (7 is monochrome VGA, 8 colour VGA).

### Routines only in sg3 and sg3a: the external transmitter

**established** for the whole bodies in sg3 (sg3a is the same code 0x10 lower). The sg3 and sg3a addresses are those minus 0x28 and 0x38. **established:** the code from `0x4b63` to `0x56e6` is the same instruction for instruction in all three images once absolute addresses are masked (686 instructions to `0x5164` and 988 to `0x56e6`, compared with the 16-bit disassembly of each image). The routines below were read in full for sg2; sg3 and sg3a follow from that identity.
- VBE function 0x03 (get current mode, `0x4f68`): **established.** Calls the ROM's own video entry with ax = 0x0f00 (`0x1c58`), and searches the table of 9-byte mode records at `0x48e0` for the record whose byte at +2 equals the returned mode with bit 7 cleared. A hit returns the record's first word in bx with ah = 0; no hit returns ah = 1 and bx = the video mode byte. Bit 15 is added to bx when the mode number the video entry returned had bit 7 set, and bit 14 when bit 3 of the register at `P+0x10` is set (`0x2213` tests it). The return is al = 0x4f.
- VBE function 0x05 (display window control, `0x4fa9`, helper `0x5064`): **established.** Calls `0x5064` and returns al = 0x4f. The helper returns ah = 3 at once when bit 3 of the byte at `P+0x10` is set (the same bit that VBE 0x03 reports as bit 14), and otherwise works on window bl (0 is A, 1 is B, anything else returns ah = 1). When bit 2 of that byte is set and bh is 0 it does the same for the other window as well. The granularity depends on bit 3 of the byte at `P+0x54`. With it set, a window position (dx for a set with bh = 0, returned in dx for a get with bh = 1) is written as the 16-bit register at `P+0x38` (window A) or `P+0x3c` (window B) holding (dx times 2) and 0x3ff, and the next register two bytes on holding that value plus 1; a get reads the first register and halves it. With it clear the position is times 8 and the second value is plus 4, and a get divides by 8. Any other bh returns ah = 1.
- VBE function 0x08 (DAC palette width, `0x531e`): **established.** For bl = 0 it picks cl = 2, or 3 when bh is above 6, and calls the vendor function al = 2 (`0x1409`, below) with that cl, returning al = 0x4f. For bl = 1 it returns bh = 6, or 8 when bit 0 of the byte at `P+0x59` is set (direct read at `0x5727`), with al = 0x4f. Any other bl returns ax = 0.
- VBE function 0x09 (palette data, `0x5355`): **established.** Accepts bl = 0, 0x80 (set, the second preceded by the wait at `0x100a`, which polls bit 0 of the byte at `P+0x5c` until it is clear and then until it is set) and 1 (get); anything else returns ax = 0x024f. It requires cx at most 0x100, dx at most 0xff and dx plus cx at most 0x100, otherwise ax = 0x014f. A set writes dl to the byte at `P+0xb0` and then cx dwords from es:di to `P+0xb4`, shifting each left by 2 first when bit 0 of the byte at `P+0x59` is clear (a 6-bit DAC) and writing it unchanged when it is set. A get writes dl to `P+0xb2` and reads cx dwords from `P+0xb4` into es:di. It returns al = 0x4f.
- VBE function 0x0a (protected-mode interface, `0x53db`): **established.** For bl = 0 it returns es:di = cs:`0x53f1` (the block the PMID section above decodes), cx = 0x1b7 and ax = 0x004f; any other bl returns ax = 0x014f.
- VBE function 0x10 (display power management, `0x55a8`): **established.** bl = 0 returns bx = 0x0710 and ax = 0x004f. bl = 1 sets a state: bh = 8 returns ax = 0x024f; otherwise it takes bh's low three bits, turns the lowest set bit into cl = its position plus one (or cl = 0 when none is set), masks cl with 3 and calls vendor function al = 0x0a with it. bl = 2 calls vendor function al = 0x0a with ch = 1, rotates 0x80 left by the result in cl, masks with 0x7f and returns it in bh. Other values of bl return ax = 0x014f. **Inferred:** the three states of bl = 1 and bh are the DPMS standby, suspend and off states, and bx = 0x0710 is the VBE/PM version with the three supported-state bits.
- VBE function 0x15 (display data channel, `0x5607`): **established.** For bl = 0 it reads the word at `P+0x20`, derives bh from which of the bits tested in it are set (0 for bits 1:0, 2 for bit 3, 4 for bits 9:8, 6 for bit 11, 3 for bit 2, otherwise 0), calls vendor function al = 0x0b, sets bh = 2 and returns ax = 0x004f. If any of bits 3:1 of the returned bl is set it keeps only bits 3:1 and forces bit 1 on; otherwise bl is returned as the vendor call left it. The word at P+0x20 is read as a port (the base comes from `0x5743`). For bl = 1 it reads the same word; if none of bits 11, 9:8, 3:0 (mask 0x0b0f) is set it returns ax = 0x014f at once without calling the vendor function. Otherwise it does the same detection (the value in dx saved from es), calls vendor function al = 0x0b with es:di as the buffer and cx = 0x80, and returns ax = 0x004f only when the first byte of the buffer is 0; otherwise, and for any other bl, ax = 0x014f. **Inferred:** the buffer holds a 128-byte display identification block whose first byte is zero.
- VBE function 0x00 (controller information, `0x4b7f`; sg3 `0x4b57`, sg3a `0x4b47`): **established.** Read in full for sg2; sg3 and sg3a run the same 84 instructions with only displaced addresses. es:di is the caller's buffer. If the dword at es:di is `VBE2` (0x32454256) the handler clears 0x100 words and copies 34 bytes (0x22) from the template block at `0x4ae4`; otherwise it clears 0x80 words and copies 20 bytes (0x14), which ends after the total-memory field. `0x505a` supplies the word stored at +0x12, the memory size in 64 KB units (below), replacing the template's value. The segment words at +8 (OEM string) and +0x10 (mode list) are set to cs. A plain request ends there with ax = 0x004f and leaves the string and mode-list pointers aimed into the ROM. A `VBE2` request moves the strings and the mode list into the caller's buffer: the OEM string pointer (+6, +8) is set to es:di+0x100 and the string is copied there, through its zero byte, by `0x5007`; the vendor-name pointer (+0x16, +0x18), the product-name pointer (+0x1a, +0x1c) and the product-revision pointer (+0x1e, +0x20) are each pointed at the next free byte and their strings copied after the previous one; the mode list pointer (+0xe, +0x10) is set to es:di+0x22 and the word list is copied there up to and including its 0xffff. So the strings run from di+0x100 and the 56 mode numbers and the terminator fill di+0x22 to di+0x93. Result ax = 0x004f.
- Mode records (9-byte records at `0x48e0`; sg3 `0x48b8`, sg3a `0x48a8`; read from the three images and as the handlers below use them): **established.** There are 57 records and a terminating word of 0xffff (at `0x4ae1`, sg3 `0x4ab9`, sg3a `0x4aa9`), byte for byte the same in all three images. The list of 56 mode numbers that function 0x00 reports (`0x486e`, sg3 `0x4846`, sg3a `0x4836`) ends exactly where the records begin; the records name the same modes plus 0x1ff, which is in the records only. Layout as the handlers read it: word 0 the VBE mode number; byte 2 the video mode number (function 0x03 matches on it, and function 0x02 passes it to the video entry or to `0x21e1`); byte 3 a class (0 for the first three records, modes 0x6a, 0x102 and 0x104; 0xa0 for the other graphics records; 0xf0 for the three text modes 0x109, 0x10a and 0x130); byte 4 a depth class (1 = 4 bits per pixel planar, 2 = 8, 3 = 15, 4 = 16, 5 = 24, 6 = 32 bits per pixel; 1 for the text records); byte 5 a value that is the same for every depth of one resolution (it forms, with byte 4, the word that `0x0a11` receives in cx; that routine was not read); bytes 6, 7 and 8 the character rows minus one, the character columns and the character cell height. The pixel width is the columns times 8. For example the record at `0x4a09` is mode 0x101: video mode 0x62, depth class 2, 80 columns, 30 rows, cell height 16 (640 by 480 at 8 bits per pixel).
- VBE function 0x01 (mode information, `0x4c4a`; sg3 `0x4c22`, sg3a `0x4c12`): **established.** Read in full for sg2 (189 instructions; the other two images run the same instructions with displaced addresses, and the call to `0x721e` lands 0x310 and 0x300 bytes later than that displacement). es:di is the buffer and cx the mode with bits 15:14 cleared. It clears 0x80 words, finds the record whose word 0 equals cx (`0x4fb1`) and gets ax, bx and dl from `0x4fc4`; a zero ax (no record) gives ax = 0x014f. Otherwise it copies the 50-byte template at `0x4b31` (sg3 `0x4b09`, sg3a `0x4af9`) over the buffer and edits it. The template is the 1024 by 768 planar block: attributes 0x1a, window attributes 5 and 3, granularity and size 0x40, window segments 0xa000, window function pointer 0x5060 (the `call` and `retf` at that address), 128 bytes per line, 1024 by 768, cell 8 by 16, 4 planes at 4 bits per pixel, 1 bank, memory model 3. Attribute bit 0 is set when the al from `0x4fc4` is nonzero. A zero bx jumps to the tail below. The window segments (+8, +0xa) are set from the word at `cs:[0x56f0]` (the `PMID` block's 0xa000); when `0x2220` finds bit 2 of the byte at `P+0x10` set, the word at +2 is set to 7 (window A attribute 7, window B attribute 0); the window function segment (+0xe) is cs; bx goes to +0x14, (dl plus 1) times 8 to +0x12 and the record's cell height to +0x17.
  - Text records (class 0xf0): bytes per scan line (+0x10) is twice the columns; attributes 0xf; window A attribute 6 and window B 0; one plane; image pages 0 and memory model 0; window A segment the word at `cs:[0x56f4]` (the 0xb800 selector); window B segment, granularity, window size and window function pointer 0; the width field (+0x12) is the column count and the height field (+0x14) is (the bx from `0x4fc4`, which for a text record is the pixel height minus 1, plus 1) divided by the cell height, stored as the whole ax of an 8-bit divide, so the remainder (zero for these records) rides in the high byte. The result is ax = 0x004f.
  - Graphics records: depth class 1 keeps the template's 4 planes at 4 bits per pixel with bytes per line equal to the columns. Class 2 sets one plane, memory model 4 (packed pixel) and 8 bits per pixel with bytes per line equal to the width. Class 3 sets memory model 6 (direct colour), 15 bits per pixel, red, green and blue field sizes 5, 5, 5 at positions 10, 5, 0 and bytes per line 2 times the width. Class 4 sets 16 bits with sizes 5, 6, 5 at positions 11, 5, 0. Class 5 sets 24 bits with sizes 8, 8, 8 at positions 16, 8, 0, bytes per line 3 times the width, and clears attribute bit 2 (already clear in the template). Class 6 sets 32 bits and bytes per line 4 times the width, keeps class 5's sizes and positions and sets no reserved field. Here bx is stored at +0x14 as returned; the text branch adds 1 to it.
  - Page count: bytes per line times the word at +0x14 is rounded up to whole 64 KB units (the high word of the product, plus 1 when the low word is nonzero); for 4 bits per pixel that count is multiplied by 4 and the memory figure replaced by 16. The memory figure (`0x505a`) is divided by the low byte of the count. A quotient of zero jumps to the tail below; otherwise the byte at +0x1d is the quotient minus 1 (0xfe for a quotient of 256 or more).
  - Linear frame buffer, for modes of more than 4 bits per pixel only: attribute bit 7 is set; the word at +0x2a is the upper word of register 0xf10 with its low nibble cleared (`0x721e` shifted right by 4, then left by 4), leaving +0x28 zero; the dword at +0x2c is the screen size in bytes (bytes per line times the word at +0x14) plus that base, so an address and not an offset from the base; and the word at +0x30 is the memory in kilobytes minus the screen size in kilobytes, with the memory in kilobytes formed in 16 bits (the figure from `0x505a` times 64, which wraps for a figure of 0x400 or more, 64 MB). **Inferred:** register 0xf10 is the public `MEM_BASE`, the PCI view of the framebuffer BAR.
  - Tail: attribute bit 5 is set unless the bits-per-pixel byte (+0x19) is 4. The result is ax = 0x004f.
- VBE function 0x02 (set mode, `0x4e18`; sg3 `0x4df0`, sg3a `0x4de0`): **established.** Read in full for sg2 (150 instructions; the others the same but for displaced addresses). bx is the mode: bit 15 is kept as "do not clear memory", bit 14 (linear frame buffer) is tested and then cleared from the lookup value. A mode of 0x13 or less takes the short path: al is the mode with bit 7 from bit 15, then ah = 0 and a call to the video entry (`0x1c58`, function 0x00 of the video interrupt); the result is ax = 0x004f. Any other mode runs `0x503f` (below) and `0x4fb1`; no record gives ax = 0x014f, and so does a request with bit 14 set for a record of depth class 1. A record of class byte 0 is set by `0x21e1` (al the video mode number, cx the record's word at +4 with bit 7 of cl set from bit 15 of the request); a nonzero return gives ax = 0x014f. A record of class 0xa0 runs `0x4fe7` (which gives ax = 0x014f if it returns al = 0), calls the video entry with al = 0x62 (the video number of mode 0x101) OR the no-clear bit, and, unless bit 15 asked to keep memory, clears the video memory: the pass count is the high word of the pixel height times the columns times 16, scaled by the depth class (class 1 halves it, class 2 keeps it, classes 3 and 4 double it, class 5 triples it, class 6 quadruples it), plus 1; each pass selects a window position through `0x2283` (positions 0, 2, 4 and on) and writes 0x8000 zero words at offset 0 of the segment at `cs:[0x56f0]`; the position goes back to 0 afterwards. It then calls vendor function 0 (`0x1409`) with the record's word at +4 in cx. Both of those paths then call `0x21fe` with ax = the request, store the video mode number at linear 0x449, the rows minus 1 at 0x484, the columns at 0x44a and the cell height at 0x485 (as a word), and point the vector at linear 0x10c (interrupt 0x43) at a font: `0x2e27` for a cell of 16, es:bp as `0x9131` returns it for 14, and `0x2614` otherwise. A record of any other class byte (the text records) calls the video entry with al = the video number OR bit 7 and skips the BIOS data stores. Every successful path ends with ax = 0x004f.
- Helper `0x503f` (sg3 `0x5017`, sg3a `0x5007`): **established.** Reads byte 1 of register 0x228 (`CRTC_OFFSET_CNTL`) by the indexed form, clears its bits 7, 5 and 1 (register bits 15, 13 and 9: the tile enable, the micro-tile enable and the XY mode enable in the public R300 header) and writes it back; then reads byte 1 of register 0xb00 (`SURFACE_CNTL`), sets its bit 0 (register bit 8, `SURF_TRANSLATION_DIS`) and writes it back. Function 0x02 runs it before every mode above 0x13.
- Helpers `0x4fb1`, `0x4fc4` and `0x4fe7` (sg3 `0x4f89`, `0x4f9c`, `0x4fbf`; sg3a `0x4f79`, `0x4f8c`, `0x4faf`): **established.** `0x4fb1` walks the mode records from `0x48e0` until a record's word 0 equals cx or the terminator is reached and returns si there. `0x4fc4` returns ax = 0 at the terminator. For a text record (byte 3 = 0xf0) it returns dl = columns minus 1, bx = rows times the cell height minus 1 and al = 0x80 (ah keeps the high byte of the product, 1 for all three text records). For any other record it loads cx from the record's word at +4 and runs the code of `0x4fe7`: save di, si, es and ds, reserve 0x3e bytes of stack as a block at bp, call `0x0a11` (not read), return al = the byte at block +2, bx = the word at +0x26, dl = the byte at +7 and ah = the byte at +0x3d, and restore. `0x4fe7` is that second half with cx from the caller.
- Helper `0x5007` (sg3 `0x4fdf`, sg3a `0x4fcf`): **established.** Copies bytes from ds:si to es:di up to and including the first zero byte.
- Helpers `0x505a`, `0x71eb` and `0x721e` (sg3 `0x5032`, `0x74fb`, `0x752e`; sg3a `0x5022`, `0x74eb`, `0x751e`): **established.** `0x71eb` reads the word at `P+0xfa` (the upper half of register 0xf8, `CONFIG_MEMSIZE`: the memory size in 64 KB units) and returns 0x80 when it is 0; `0x505a` is that routine with bx saved. `0x721e` reads the upper word of register 0xf10 through the indexed form (`0x58e1`) and shifts it right by 4.
- Helpers `0x7245` and `0x7269` with the table at `0x7260` (sg3 `0x7555`, `0x7579`, table `0x7570`; sg3a `0x7545`, `0x7569`, table `0x7560`): **established.** `0x7245` reads the byte at `P+0x51` (bits 11:8 of `CRTC_GEN_CNTL`, the public pixel-width field), keeps the low nibble capped at 8 and looks it up in the nine-byte table 0, 4, 8, 16, 16, 24, 32, 16, 16 (bits per pixel). `0x7269` adds 4 to that and shifts right by 3, so the bytes per pixel are 0, 1, 1, 2, 2, 3, 4, 2, 2 (4 bits per pixel counts as one byte).
- Helper `0x22b1` (sg3 `0x2289`, sg3a `0x2279`): **established.** Reads the byte at `P+0x53` (bits 31:24 of `CRTC_GEN_CNTL`) and tests its bit 0 (register bit 24, the public `CRTC_EXT_DISP_EN`), leaving the zero flag set when it is clear. VBE functions 0x06 and 0x07 return ax = 0x024f when it is clear. **Inferred:** that is how they refuse in a standard VGA mode; the mode state the bit tracks was not read.
- VBE function 0x04 (save and restore state, `0x50fb`; sg3 `0x50d3`, sg3a `0x50c3`): **established.** Read in full for sg2 (the other two the same but for displaced addresses). dl is the request (0 size, 1 save, 2 restore; a larger dl gives ax = 0x014f), cx the state mask, es:bx the buffer. First the handler scans the segment words of the first 60 interrupt vectors (linear 2, 6, 10 and so on) and goes on only if one is nonzero and below 0xa000; if none is, it returns ax = 0, not 0x4f, with bx the caller's. A mask whose low nibble is zero gives ax = 0x014f. A restore with mask bit 3 set calls `0x73b6` (not read) with ds = es and es from `cs:[0x56f2]`. A save asks function 0x04 itself for the size (`0x4f04` with dl = 0 through `0x1c58`) and zeroes that many 64-byte blocks at the buffer. All three requests then call the video entry's function 0x1c with al = dl and the same mask and buffer. With mask bit 3 clear the result is ax = 0x004f. With it set, a size request adds 0x3b blocks to the count the video entry returned in bx, a save exchanges the word at es:[bx+6] with 0, putting the old value in di, and calls `0x730c` (not read) with al = 0 and ds from `cs:[0x56f2]`, and a restore does nothing more. **Inferred:** the extra 0x3b blocks and the two unread routines hold the chip's own register state.
- VBE function 0x06 (logical scan line length, `0x519e`; sg3 `0x5176`, sg3a `0x5166`): **established.** Read in full for sg2. bl 0 sets the length in pixels (cx), bl 2 in bytes, bl 1 gets the current length and bl 3 the maximum; a larger bl gives ax = 0x014f, and a clear `0x22b1` gives ax = 0x024f. A set converts bytes to pixels by dividing cx by the bytes per pixel (`0x7269`), turns pixels into characters (shift right by 3, minus 1, bit 0 cleared), reads bits 23:16 of register 0x200 (`CRTC_H_TOTAL_DISP`, by `0x58a2`) plus 1 and raises the value to it when it is larger, returns ax = 0x024f when the value is above 0x3fc, then stores it at linear 0x44a and writes it to register 0x22c (`CRTC_PITCH`) by the indexed write. A get (bl 1) goes straight to the report. For bl 3 it reads bits 26:16 of register 0x208 (`CRTC_V_TOTAL_DISP`) plus 1, starts at 8160 pixels (0x3fc characters) and takes 32 pixels off until the video memory (`0x505a` times 65536 bytes) divided by the bytes per line is at least that figure. Every path ends in the same report: cx is the characters at linear 0x44a times 8 (or the width just found), bx the bytes per scan line (cx times the bytes per pixel), dx the number of scan lines that fit in memory (`0x505a` times 65536 divided by bx, limited to 0xffff) and ax = 0x004f.
- VBE function 0x07 (display start, `0x5281`; sg3 `0x5259`, sg3a `0x5249`): **established.** Read in full for sg2. A clear `0x22b1` gives ax = 0x024f. bl 0 or 0x80 sets: the start in bytes is ((the columns word at linear 0x44a times dx, times 8) plus (cx with its low three bits cleared)) times the bytes per pixel from `0x7269`, formed by repeated addition that runs 65536 times when `0x7269` returns 0, and it is written to register 0x224 (`CRTC_OFFSET`) by the indexed write; with bl 0x80 the handler first runs `0x100a`, the retrace wait described under function 0x09. A set returns every register as it was passed. bl 1 gets: it reads register 0x224, keeps its low 27 bits and divides by the bytes per scan line (columns times 8 times bytes per pixel), returning the quotient in dx (the first displayed line) and the remainder divided by the bytes per pixel in cx (the first displayed pixel); bx is left holding the bytes per pixel. Any other bl gives ax = 0x014f. Result ax = 0x004f.
- Stub `0x56e2` (sg3 `0x56ba`, sg3a `0x56aa`): **established.** The word table at `0x56b6` sends VBE functions 0x0b to 0x0f and 0x11 to 0x14 here; the stub is `mov bx,ax` and `ret`, so those functions return ax = the caller's bx and nothing else changes.

- Vendor function 0x0a (`0x12f8`; sg3 `0x12c6`, sg3a `0x12b6`) and helper `0x13af` (sg3 `0x1387`, sg3a `0x1377`): **established.** Read in full for sg2; the other two the same but for displaced addresses (the register calls land 0x30f and 0x2ff bytes lower). Any other ch returns ah = 1. **Inferred:** cl 0 to 3 are the on, standby, suspend and off display power states, the same ones VBE function 0x10 passes; the register names are the public ones.
- Vendor function 0x0b (`0x132e`; sg3 `0x12fc`, sg3a `0x12ec`): **established** for the handler, which differs in sg3 and sg3a as the dispatcher entry says. In sg2 it limits cx to 0x100, passes ax as bx to `0x5dbb`, stores that routine's bx and ax in the saved registers and leaves ah as `0x5dbb` set it. `0x5dbb` is **located** only: it picks a table pointer from `cs:[0x5cff]`, `cs:[0x5d01]` or `cs:[0x5d03]` by bh (2, 0 or 4, with checks on bl and `0x5fc8` or `0x5fd7`) and returns ah = 1 for an unsupported combination. **Inferred:** this is the display-data read that VBE function 0x15 calls.
- Vendor function 0x0c (`0x1346`; sg3 `0x131e`, sg3a `0x130e`) and `0x72ae` (sg3 `0x75be`, sg3a `0x75ae`): **established.** Read in full for sg2 down to the callees named below. `0x72ae` disables interrupts, then selects on cl: 0 returns cx = 0x124d; 1 runs `0x72f6`, which sets es from dx, keeps di as the area start, advances 0x20 bytes, runs `0x4133`, `0x41a5` and `0x42b2` (not read) and then `0x730c`; 2 runs `0x743e`, which runs `0x73b6` and then `0x41f3`, `0x425b` and `0x42ff` (not read); 3 writes the word at `cs:[0x13e]` to port `P+0x16` (P is bx when bx is nonzero), runs `0x6552` (ASIC init 2) and the PLL script interpreter `0x6a49` with the table at `0x58f`. Any other cl returns ax = 0x100. All paths other than that restore the flags and return ax = 0 to the handler, which stores cx and ax in the saved registers. **Inferred:** sub-functions 1 and 2 save and restore the chip state around a mode change, and 3 re-runs the chip initialisation.
- Routines `0x730c` and `0x73b6` (sg3 `0x761c` and `0x76c6`; sg3a `0x760c` and `0x76b6`): **established** for the register traffic, **located** for their unread callees. Both are the SVGA state routines VBE function 0x04 calls. `0x730c` stores the offset of its register block from the area start at es:[bx+8], clears bit 5 of the byte at `P+0x2b` and sets it again when the byte of register 0x3f8 (`CRTC2_GEN_CNTL`) at bits 31:24 has bit 1 set, then reads the 64 dwords at `P+0` to `P+0xfc` into es:di, where the dword at `P+0xc` stored is a second read of it made with the byte at `P+8` (the clock index) set to 0 and then restored. It clears bit 5 of the byte at `P+0x7c` (`DAC_CNTL2`), runs `0x74e3` (not read), sets the bit again when `P+0x2b` bit 5 is set and runs it again, writes the saved byte back, then stores the indexed registers 0x100 to 0x1ff and 0x200 to 0x2ff (64 dwords each: write the index to `P+0`, read `P+4`) and runs `0x747b`, and if `P+0x2b` bit 5 is set also stores 0x300 to 0x3ff. It ends by calling `0x69a8` with di the entry value plus 0xd34 (not read). `0x73b6` is the reverse: from the block at ds:bx+[bx+8] it writes the 64 dwords back to `P+0` to `P+0xfc` except the dword at `P+0xc` and the one at `P+0xac`, keeping only bits 9:8 of the low word of the dword at `P+8`; clears and restores `DAC_CNTL2` bit 5 around `0x74ff` (not read) as `0x730c` does around `0x74e3`; writes back the indexed registers 0x100 to 0x2ff by `0x7467` (and 0x300 to 0x3ff when `P+0x2b` bit 5 is set), runs `0x74af` and ends by calling `0x69f6` with si the entry value plus 0xd34 (not read).
- Vendor function 0x0d (`0x1355`; sg3 `0x132d`, sg3a `0x131d`) and helper `0x0f17` (sg3 `0x0ee5`, sg3a `0x0ed5`): **established.** Read in full for sg2. The handler passes ax as bx to `0x0f17` and stores the returned ax. With bl = 0, `0x0f17` writes at es:di (es from dx) five (id, value) word pairs, ids 0x12, 0x6a, 0x55, 0x83 and 0x84, and then the words 0, 0, 0xffff, 0xffff, returning ax = 0. Each value is what `0x0fc1` returns for the id: the byte at `P+0x18` for an id of 0x62 or 0x12, `P+0x19` for 0xe5 or 0x6a, `P+0x1a` for 0x55, `P+0x1b` for 0x83 and `P+0x1c` for 0x84, in each case with bit 7 set (any other id gives its own bit 7). With bl = 1 it reads the value word of each of the five pairs at es:di (the first word of a pair is skipped) and writes its low byte to `P+0x18` to `P+0x1c` in that order, returning ax = 0. With bl = 2 it returns ah = 1 (`0x0f96`). With bl = 3 it runs `0x0f99`, which builds a 0x20-byte block on the stack whose five value words are 0, 4, 4, 0x10 and 0, and runs the bl = 1 case on it, so `P+0x18` to `P+0x1c` become 0, 4, 4, 0x10, 0; it returns ah = 0. Any other bl returns ah = 1. **Inferred:** the five bytes at `P+0x18` to `P+0x1c` lie in the BIOS scratch registers (bytes 0 to 3 of `BIOS_2_SCRATCH` at register 0x18 and byte 0 of `BIOS_3_SCRATCH` at 0x1c in the public header) and are keyed by the ids of five resolutions in the table at `0x101e` (the ids the table gives for 640 by 480, 800 by 600, 1024 by 768 and 1280 by 1024, plus 0x84, which the table does not list); this function saves and restores them. The reading of the five bytes as one setting per resolution is the code's shape, not a decoded meaning.
- Vendor function 0x14 (`0x1361`; sg3 `0x1339`, sg3a `0x1329`) and `0x1412` (sg3 `0x13ea`, sg3a `0x13da`): **established.** Read in full for sg2; the other two the same but for displaced addresses. `0x1412`: if bit 0 of cl is set it runs `0x7641` and replaces bits 1:0 of the byte at `P+0x20` with its result (`0x60c7` with ah = 3); if bit 0 of ch is set it does the same with `0x7674` and the byte at `P+0x21` (`0x60be`). It then keeps bits 14, 7 and 6 of cx, reads the word at `P+0x20`, clears bits 14, 7 and 6 of it, ORs in the kept bits, clears bit 7, writes it back, reads it back into cx, and swaps bits 7 and 6 of cl (bit 6 becomes bit 7 and bit 7 becomes bit 6; ch is unchanged). The handler stores that cx in the saved cx and returns ah = 0.
- Vendor function 0x15 (`0x136b`; sg3 `0x1343`, sg3a `0x1333`): **established.** Read in full for sg2. For ch = 0 it returns in cl the byte `0x6145` gives (the byte at `P+0x27`, bits outside 0xab cleared) shifted right by 1, with ah = 0. For ch = 1 it forms ah as cl shifted left by 1, runs `0x60db` (which builds a status byte in cl from bits tested in the word at `P+0x20`), ANDs ah with it, and when the result is nonzero writes ah to `P+0x27` through `0x6136` and returns ah = 0; a zero result returns ah = 1; any other ch returns ah = 1.
- Vendor function dispatcher (`0x115a` and `0x1161`, sg3 `0x1128` and `0x112f`, sg3a `0x1118` and `0x111f`): **established.** Pushes ds, es and the 32-bit registers, takes al as the function number (ah is loaded from the byte at `cs:[0x129]`, which is 0xa0, by `0x1161`), and returns with `0x13a7` (byte at +0x1d of the saved eax set to 2) for 32 or more. Every handler leaves its result in the saved registers and ends through `0x1397` (ah = 0), `0x139f` (ah = 1) or that 2. The word table at `0x1182` (sg3 `0x1150`, sg3a `0x1140`) holds handlers `0x11c2`, `0x11ce`, `0x11d4`, a stub `0x1390` for function 3, `0x11eb`, `0x1210`, `0x1237`, `0x1264`, `0x127c`, `0x1297`, `0x12f8`, `0x132e`, `0x1346`, `0x1355`, the stub for functions 14 to 19, `0x1361`, `0x136b` and the stub for functions 22 to 31. The code of the thirteen handlers other than 0x0b is the same in all three images with a displacement of 0x32 (sg3) and 0x42 (sg3a) for functions 0x00 to 0x0b and 0x28 and 0x38 for functions 0x0c and up (the table's later entries and the stub); the function 0x0b handler differs in sg3 and sg3a (below).
- Vendor function 0x00 (`0x11c2`) and 0x01 (`0x11ce`): **established.** Function 0 first calls `0x71a7`, which returns ah = 1 for cl above 8 and otherwise loads es from dx when ch is 0x81, limits cl to 8 and calls `0x09e8`; when ah comes back nonzero the handler returns ah = 1. It then sets cl = 1 and falls into the body of function 1, which calls `0x71c3` with cl as it stands and returns ah = 0. `0x71c3` loads ax = 0x0a02 and, when bit 0 of cl is set, replaces it with the low nibble of the byte at `P+0x51` (capped at 8) in ah and 3 in al; it clears bits 2 and 0 of the byte at `P+0x53`, ORs al (2, or 3 when cl bit 0 was set) into it, and calls `0x6f5c` with ah.
- Vendor function 0x02 (`0x11d4`): **established.** Takes the low two bits of cl as an index into the four bytes at `0x11e7` (9, 0, 10, 11), calls `0x6f5c` with that byte in ah, and returns ah = 0. The first steps of `0x6f5c` are an index into the byte table at `0x6f40`, a write of 0xff to the byte at `P+0x5b`, and an update of the byte at `P+0x59` by an AND mask 13 bytes further on in that table and an OR value from the entry (the DAC programming slot of the ATI header); the routine's later steps are not read here.
- Vendor functions 0x04 to 0x07 (`0x11eb`, `0x1210`, `0x1237`, `0x1264`): **established.** Each stores values into the saved registers and returns ah = 0 through `0x1397`. `0x11eb` stores ch = 0x70, dx = 0x01ff, bx = 0x1a20 (ah from `0x7233`, al = 0x20), si from `0x7215` and di from `0x720c`. `0x1210` stores cx = the low nibble of `cs:[0x129]` (0), dx = the base `P` from `0x5743`, di = the word at `P+0x14` and si = the word at `cs:[0x13e]`. `0x1237` stores cx = the word `0x71eb` returns shifted right by 3, bx from `0x721e`, si and di from the low and high halves of the dword `0x722a` returns, dx from `0x71fa` and the saved al from `0x7203`. `0x1264` stores cl = 0x80 (the byte `0x0d1c` returns), dx = cs, di = `0x661c` and si = `0x670e`, which in sg2 are the offset of the maximum-colour-depth table (header slot +0x2c) and another address 0xf2 on. What the callees compute is outside these bodies.


The VESA information block, mode list and `PMID` block are decoded above. The handlers behind these tables are **located** only; see [open-questions.md](open-questions.md#option-rom).

## What the IRIX software does with the images (cross-reference)

The kernel attach path has its own reader; these are only pointers from the strings and short routines.

- **established.** `usr/gfx/VOYAGER/bin/sg2flash` (stripped, N32) carries a table of six records in `.data` at 0x100086d8. The first three are an id string, a file name and a size word: `10024E44` with `9700.bin`, `10024E47` with `sg2.bin`, `10024E4B` with no name; the size word is 0x40000 for the two named records. The next three have the id `10024E4B` and a file name, plus a mask and a value: `sg3.bin` with mask 0xc0 and value 0x40, `sg3a.bin` with mask 0xc0 and value 0, and `sg3b.bin` with mask 0 and value 0. `9700.bin` and `sg3b.bin` are not in the install. The ids read as the PCI vendor (1002) and device (4E44, 4E47, 4E4B) in hexadecimal; 0x4e44 is the public R300 Radeon 9700 device ID.
- **established.** In `do_card` the three-record loop (stride 104, three records, only those whose id equals the first-level record's) takes the register word at offset 0x1a4 of a memory mapping (a `base/2.be` file of 8192 bytes), skips a record whose mask is 0, and selects the record whose value equals the word ANDed with the mask. It prints `vippad_y = 0x%x file = %s`. So the choice between the two X2 images is made by bits 7:6 of that register word: 01 selects `sg3.bin`, 00 selects `sg3a.bin`.
- **inferred.** The offset 0x1a4 is `GPIOPAD_Y` in the public Linux header, a pad input register. The strap bits on the card that feed them are **unknown**, and what the strings' "vippad" name means for the R350 is **unknown**.
- **established.** Who reads offset 0x1a4 at run time. Of the shipped IRIX objects, only `fglrx_drv.so` reads it through a constant offset from the register aperture, at eleven sites in two static routines. The kernel objects (`fglrx.o`, `is1.o`, `vgastubs.a` and every `vga.a` member) have no constant-offset load or store of 420 from a register base; the only two accesses of that offset in `fglrx.o` (0xea0c and 0xea20, in `drm_ioremap`) read and bump a counter in the driver's own record. Accesses through computed offsets in the kernel objects were not traced. In the X module, the code at 0x411d40 (a stretch of unlabelled code; for chip codes 44 and 52 with the byte at driver +190 nonzero, 0x411d9c) saves `GPIOPAD_MASK` (0x198) and `GPIOPAD_EN` (0x1a0), stores 4 to the first and 0 to the second, reads 0x1a4 (0x411dbc) and tests bit 2. With bit 2 set it restores both registers, logs "No TV dongle present" at level 7 and returns 0 (0x411dc8 to 0x411e00); with bit 2 clear it restores them and, when the driver word at +180 is 3, goes on to program the TV block at `TV_MASTER_CNTL` (0x800, 0x411e20). The routine at 0x421080 holds the other ten sites. It returns at once when the driver word at +9312 is zero. Otherwise it sets or clears bit 10 of `MDGPIO_A` (0x1ac) by bit 3 of the driver word at +72, clears bit 25 of register 0x50 (`CRTC_GEN_CNTL`; bit 25 is `CRTC_EN` in the public header, so this stops the CRTC), then reads 0x1a4 against the mask 0x10000 (loaded at 0x42108c): five reads per pass until a read shows bit 16 clear (0x4210c8 to 0x421110), then five reads per pass until a read shows it set (0x421118 to 0x421160), and last writes register 0x50 back with its old value ORed with 0x2000000, which starts the CRTC again (store in the delay slot of the return at 0x421168). So this X module never uses 0x1a4 to choose an option ROM: it reads bit 2 as a TV-dongle detect line and uses a low-then-high transition of bit 16 to restart the CRTC (**inferred** to be an external sync input, from the CRTC restart on the edge), while only `sg2flash` uses bits 7:6 to pick between the two X2 images. AMD's M56 register reference (an R5xx-generation chip, later than the R350, whose register map differs in other places) lists the same four offsets as `GPIOPAD_MASK` (0x198), `GPIOPAD_A` (0x19c), `GPIOPAD_EN` (0x1a0) and `GPIOPAD_Y` (0x1a4) and describes `GPIOPAD_Y` as the read-back of the GPIO pad inputs, bits 17:0 (**inferred** to hold for the R350, from that matching layout). So bits 7:6 are the input levels of the pads numbered 6 and 7, and the "vippad_y" in the flash tool's message is the pad-input register. Which board strap drives those two pads is **unknown**: no shipped software or published source read in this workspace depends on the wiring (routes tried: the kernel objects, the X module, the flash tool, the Linux and X.Org headers, the R3xx 3D register reference, which has no GPIO section, and the M56 reference).
- **established.** The tool opens `config` of the device under `/hw/.id/pci/`, reads a 32-bit word with ioctl code 0x40040030 and writes it back with bit 0 set using 0x80040030 (**inferred** to be PCI configuration offset 0x30, the expansion ROM base address, with its enable bit), maps `rom.le` (0x20000 bytes), reads the image file named by the record, finds the `VER%d.%d.%d.%d` string in both, and prints both ("File version", "Card version"); `-F` forces the flash, and "Couldn't read version from rom. Force to flash." suggests an unreadable card version also leads to a flash. The image file comes from `usr/gfx/ucode/VOYAGER/` under the directory `GL_GRROOT` names. The messages name two flash types, "ST flash" and "Atmel flash", with write-enable, bulk-erase and idle-poll steps ("SFWriteST", "SFWriteATMEL").
- **inferred.** The ROM is held in a serial flash on the card, which the chip programs by register writes; `sg2flash` is how the images in this chapter get onto the card. How it compares two versions is read in the next entry.
- **established.** The version comparison in `sg2flash`, read in full from `do_card` (0x1000397c) and its two static helpers (named here by address, since the binary has no symbol for them). The options are `getopt` string "f:hqvF": `-h` prints usage, `-q` sets the query flag (the .bss word at gp -32508), `-F` sets the force flag (gp -32512), `-v` sets the verbose flag, and `-f` is accepted and takes an argument that the option loop does not use. `do_card` reads the whole image file into memory, then calls `sub_10001388` (buffer, length, pointer to four words) on it, and a second time on the 0x20000-byte mapping of the card's `rom.le`. `sub_10001388` scans the buffer a byte at a time; at each byte equal to 0x56 it calls `strncmp` against the three-byte string "VER" (the first word of .srdata at 0x10008a48) and, on a match, `sscanf` with "VER%d.%d.%d.%d". It stops at the first position where all four numbers parse; if no position parses it prints "Version string not found" and returns 1, otherwise it returns 0. A failure on the file stops `do_card` with "Couldn't find version in file". A failure on the card's ROM prints "Couldn't read version from rom. Force to flash.", sets the force flag, and the tool flashes regardless (unless `-q` is set, which only prints the card version: "Current card BIOS version is: %d.%d.%d.%d" is the query output). With both versions parsed and `-F` not set, `do_card` calls `sub_100014c4(file version, card version)`, which prints both and compares the four numbers as unsigned words, first number first: it returns 1 when the card's number is below the file's at the first position that differs, and 0 when the file's is below the card's or when all four are equal. A nonzero result starts the flash, a zero result skips it, so the tool reflashes only when the card holds an older version than the image (and never to downgrade or to rewrite an equal version without `-F`). Flashing prints "Flashing card at %s" and calls `flash_rom` up to five times, stopping at the first zero return and printing "flash_times = %d" after each failed call. The register word at offset 0x1a4 that selects the image is loaded with one `lw` from the `base/2.be` mapping (0x10003cfc, `lw a2,420(s6)`); only when that `mmap` returns -1 does the tool open `base/2.le` instead and byte-reverse the word in registers (loads and shifts at 0x1000407c to 0x100040a0), so the masked value is the same in both cases.
- **established.** `vga_shadow_bios` in `vga.a` (whole body read) takes a board record with a ROM pointer and a length, accepts the image when bytes 0 and 1 are 0x55 and 0xaa, or when bytes 3 and 2 are 0x55 and 0xaa (a word-swapped read), allocates kernel memory, copies the image into it, and byte-reverses each 32-bit word in the second case. The strings in `vga.a` name an x86 emulator (`xf86InitInt10`, `run_bios_int`, `setup_system_bios`) and the failures "ROM NOT PRESENT", "ROM SIG INVALID !", "ROM SHADOW failed" and "BIOS INIT FAILED". `bios_checksum` in the same archive sums bytes, **inferred** from the head of its loop to be the 8-bit sum that is 0 for all three images.
- **inferred.** This is the kernel counterpart of the init-entry code above: the host copies the ROM, runs its x86 initialisation in an emulator, and the BIOS then holds the VESA and table data. What the host does after the emulated BIOS returns (register state, mode set) is **unknown**.
- **established.** `biosemu` (usr/diags/SG/bin) names `pciba_enable_rom`, `rom.le`, a ROM shadow copy and the check "ROM SIGNATURE INVALID: 0x%x,0x%x". `libint10.so` (X module) names "Looking for BIOS at PCI:%i%i%i", `mapPciRom` and "Bad V_BIOS checksum". `libvbe.so` prints "VESA VBE OEM Product" and "OEM Product Rev", which are the strings in the VESA block above. The X module `fglrx_drv.so` names "Video BIOS not detected, using default PLL parameters!", "No Panel Info Table found in BIOS!", "Incorrect sig for BIOS TV Info block" and "Connector Layout from BIOS". None of these paths was read; they locate the consumers only.
- **established.** `fglrx_attach` in `fglrx.o` holds the messages "ROM NOT VALID", "ROM present - but sig NOT VALID" and "cannot get to ROM space", and compares two bytes read from the ROM against 0xaa and 0x55 (at offsets 0x1b8c and 0x1b98 of the object's text). Which bytes and what it does with a valid ROM are **unknown**; the attach reader owns that.
