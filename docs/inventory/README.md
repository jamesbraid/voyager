# Inventory

Every file in this directory is generated by `retools/tools/inventory.py`. Do not edit them by hand: change the docs, the headers or `scripts/inventory-config.json`, then regenerate. The script is the same in every graphics workspace; what belongs to one graphics family (the files in scope and their roles, the register windows and how code reaches them, the token sources, the microcode images, the specification tables) is in the config. The same inputs give byte-identical tables.

Run it from the repository root with `root/` populated (`IRIX_FILES.md`), inside the toolchain environment of `AGENTS.md` section 5:

    python3 retools/tools/inventory.py

It also rewrites the block between the `inventory:begin` and `inventory:end` markers at the top of [../coverage.md](../coverage.md). Regenerate in the same commit as any doc or header change.

## Reproducible runs

The tables are a function of three inputs. The script checks each before it writes anything and, if a check fails, stops with every problem listed and leaves the tables alone.

- **The binaries.** `scripts/inventory-root.sha256` has a `sha256  path` line for every file under `root/` that a run reads: the files of the configured binaries, the root files the config names, and any indexed document that is a link into `root/`. The run hashes them and fails when one is missing (a dangling link counts as missing), one is not listed, or a hash differs. Only content counts, so `root/` can be a real directory, a symlink to a shared copy or a mount. Write the manifest from a complete `root/` with `--update-root-manifest`.
- **The sibling workspaces.** The cross-workspace role check reads each sibling's documents at the commit recorded in `scripts/inventory-siblings.json`, exported from that commit with `git archive`, not from the working tree. The checkout only has to contain the commit. The script looks for a clone at the config's path (`../odsy`) and then at `.cache/siblings/<name>`, which is the place for a run in a container that mounts only this workspace. A sibling that is missing, lacks its recorded commit or belongs to this workspace's own family (it would grade the workspace against itself) fails the run. `--update-pins` moves each pin to the sibling's HEAD; commit the file with the tables made from it. `--skip-siblings` runs without the check and writes `skipped` into the tables: use it to look, not to commit.
- **Merge conflicts.** An input with a line that starts `<<<<<<<`, `>>>>>>>` or `|||||||` fails the run, naming the file and line. The generated block of `coverage.md` is rewritten whole, so markers inside it do not count.

`summary.tsv` records them after the per-table rows: `input root manifest` (the file count in `rows`, the manifest's sha256 in `input`) and one `input sibling <name>` per sibling (its commit, or `skipped`). The `coverage.md` headline repeats them. Rows and files are sorted, text is read and written as UTF-8 and the tools run under the C locale, so the same commit, manifest and pins give byte-identical tables from any clone, with any `--jobs`.

A setup that reproduces them:

    mkdir -p .cache/siblings
    git clone <sibling repository> .cache/siblings/<name>    # each sibling; ../<name> also works
    ln -s <shared checkout>/root root                        # or a copy or a mount that matches the manifest
    python3 retools/tools/inventory.py

When a rebase or merge conflicts in `docs/inventory/*.tsv`, do not resolve it by hand. `.gitattributes` marks those tables `-merge`, so git never line-merges them and stops with this side's copy and no markers. Take either side, run the script, and `git add docs/inventory docs/coverage.md`. `audits.tsv` is kept by hand and merges normally.

## Tables

Every table except `summary.tsv` ends with the same three columns:

- `status`: one of the five statuses below.
- `doc`: where the best mention is, `file#anchor` for a markdown page and `file:line` for a header.
- `section`: the heading of that page section, or the section banner of that header.

A table that does not apply to this family is still written, with its header row and no rows.

### binaries.tsv

One row per distinct file content in scope. An archive contributes one row per member; byte-identical files and members are read once.

| Column | Meaning |
|---|---|
| `binary` | install path under `root/`, with `(member)` for an archive member |
| `group` | the config group that put it in scope |
| `role` | `board-` or `shared-` followed by what it is: `kernel`, `library`, `x-module`, `x-server`, `tool`, `diagnostic`, `firmware`, `microcode` or `data`. `board-` means it serves this family only |
| `kind` | `object`, `executable`, `shared-object` or `data` |
| `abi` | `o32`, `n32`, `n64`, or `-` for data |
| `bytes` | size |
| `sha256` | first 16 hex digits of the content hash |
| `copies` | the other paths with the same content |
| `functions` | rows this binary has in `functions.tsv` |
| `address_source` | which sources gave the binary's function addresses: `symtab`, `dynsym`, `mdebug`, `dwarf`, joined by `+`, or `strings` (names only), with a note when stale DWARF addresses were dropped; see Function addresses |
| `access_sites` | register access sites resolved to an offset |
| `unresolved_sites` | register access sites whose offset could not be traced |

The status of a binary comes from its file or member name, written in backticks.

### functions.tsv

One row per (binary, function symbol). A function present in several distinct binaries has one row in each; `summary.tsv` also counts distinct names.

| Column | Meaning |
|---|---|
| `binary`, `role`, `abi` | as in `binaries.tsv` |
| `elf_section` | the section holding the code |
| `address` | the symbol value from the source `address_source` names for the binary (0 when only a name is known) |
| `size` | the symbol size; when the symbol has none, the distance to the next function in the section |
| `name` | the symbol |
| `source` | where the name came from: `symtab`, `dynsym`, `mdebug` (o32 procedure table), `funcnames` (`.debug_funcnames`), `dwarf`, or `strings` (names found by pattern in a raw image) |
| `code_sha` | first 12 hex digits of the hash of the function's bytes, empty when they could not be read. A name with the same `code_sha` in two binaries has the same code there |
| `rejected` | `multi-unit` (the name is defined at several addresses in the binary), `shared-address` (another name has the row's address), `address-unknown` (no source gives the function an address; see Rows with no address), these joined by `+`, or empty; a `shared-address` row is at most `named-only` unless an entry gives its binary and exact address, a `multi-unit` row needs an address inside it (see Function rows the generator rejects) |
| `scope` | `in`, or `out:N` when rule N of the config's `scope` list excludes the function (see Scope) |

### mmio.tsv

One row per register offset the code reaches, in a window of the config.

| Column | Meaning |
|---|---|
| `window` | the register window, or the named region of one |
| `offset` | offset from the window base |
| `name` | the register a specification table puts at this offset, if any |
| `access` | `r` or `w` and the width in bytes, for each kind seen; `alias` marks an access through an alias the config folds back |
| `sites` | instructions or accessor calls that reach it |
| `binaries` | how many binaries reach it |
| `functions` | the functions that reach it, the first six by name |
| `evidence` | how the base was known: a constant address, a pointer field, a global, an argument, an accessor, `caller argument` (every call site passes the same window) or `callee return` (the callee always returns it) |
| `example` | the first `binary:function` by name |

### tokens.tsv

One row per command token or constant command word.

| Column | Meaning |
|---|---|
| `kind` | `token` (a named host command), `word` (a constant stored to a command register or FIFO), or a group the config defines over words, such as `block` |
| `value` | the token or word |
| `name` | the names the token tables give it |
| `register` | the register the word was stored to, for families whose words are register-specific |
| `detail` | fields of the word, or what a token table says about the token |
| `sources` | the tables and code scans that list it |
| `sites`, `binaries`, `example` | as in `mmio.tsv`, for words found in code |

### ioctls.tsv

One row per ioctl number a kernel dispatcher handles or user code sends.

| Column | Meaning |
|---|---|
| `number`, `hex` | the request number in decimal and hex |
| `table` | the dispatcher table that serves it, or the number range it falls in |
| `handler` | the kernel functions that handle it |
| `evidence` | `table` (a dispatch table entry), `handled` (a constant the dispatcher compares against), `boundary` (a compare boundary of a binary search, next to a case but not always one), `sent` (a constant argument of an ioctl call), `constant` (a constant of the family's ioctl pattern built anywhere) |
| `senders` | the functions that send it |
| `binaries`, `example` | as in `mmio.tsv` |

### ucode.tsv

One row per microcode routine, label, symbol or dispatch entry.

| Column | Meaning |
|---|---|
| `program` | the microcode image |
| `kind` | what the row is, from the config (`symbol`, `label`, `dispatch slot`, `host entry` and so on) |
| `address` | address, record number or slot index |
| `name` | the symbol or label, if the image has one |
| `detail` | sizes, handlers, flags |

### spec-registers.tsv

One row per register a specification or a shipped register table lists.

| Column | Meaning |
|---|---|
| `spec`, `table`, `page` | where the register is listed |
| `window`, `offset` | where it sits, in the windows of `mmio.tsv` |
| `name` | its name there |
| `count`, `stride`, `width`, `rw` | array length, array stride in bytes, width in bits, access |
| `reached_in_code` | `mmio.tsv` rows inside it |

### summary.tsv

One row per table, plus `functions (distinct names)`, which counts each function name once at its best status, then the `input` rows (see Reproducible runs), and then one row `functions in <binary>` per binary that has functions.

| Column | Meaning |
|---|---|
| `table`, `rows` | the table and its row count |
| `out_of_scope` | rows a scope rule excluded; `rows` and every other count leave them out. For `functions (distinct names)`, the names all of whose rows are excluded (see Scope) |
| `understood`, `located`, `named_only`, `undocumented`, `no_software_dependency` | rows at each status |
| `understood_with_open` | understood rows whose entry also says a sub-fact is `unknown` (see Open sub-facts). They are counted in `understood` too, so the open facts stay visible |
| `understood_distinct` | different sentence skeletons behind the understood rows |
| `templated` | rows held at `located` because their entry's skeleton is over the template cap |
| `pct_understood` | understood rows as a percentage |
| `pct_located_or_better` | understood, located and no-software-dependency rows as a percentage |
| `pct_mentioned` | every row except `undocumented`, as a percentage |
| `pct_done` | understood and no-software-dependency rows as a percentage |
| `unresolved_sites` | for `mmio`: register access sites whose offset could not be traced |
| `truncated` | for `ucode`: a table the config reads in part, as `program: N of M entries`; empty when every entry is read |
| `audited_real_pct`, `audited_sample`, `audited_date` | the latest independent audit of the table: the share of the sampled understood rows that held up, the sample size and the date, read from `audits.tsv`; empty when the table was never audited |
| `computes` | for `ucode` only: understood rows whose entry describes an operation on data (see What understood means). Empty for every other table |
| `reused` | rows held at `located` because their entry's role text is a sibling workspace's (see Cross-workspace role check) |
| `input` | on the `input root manifest` and `input sibling <name>` rows only: the sha256 of the root manifest, or the sibling's commit (`skipped` when the check did not run). See Reproducible runs |
| `multi_unit`, `shared_address` | for `functions` and `functions in <binary>` rows: rows rejected for a name defined at several addresses, and for an address several names share; empty for other tables |
| `address_unknown` | for `functions` and `functions in <binary>` rows: rows with `rejected` = `address-unknown`, which `rows` and every other count leave out (see Rows with no address); empty for other tables |

### audits.tsv

Committed by hand, not generated: one row per table per independent audit (an auditor who did not write the entries re-derived a random sample of understood rows from the binaries). Columns: `table`, `date`, `sample`, `real`, `shallow`, `wrong`, `note`. The percentage is `real` over `sample`. The audit measures the claims; the other columns measure what the entries say, so a table can be 100 % understood and still be audited at 60 %. Append a row after each audit; for a table the latest date is shown.

## Status

A mention is not understanding. The status of an item is the best of the entries that mention it, and an entry earns its status only for its subject. An entry is one table row (its own cells only, never the header), one list item with its continuation lines, one paragraph, or one header comment paragraph with the definition it sits on. A fenced listing restates its subject and never earns more than `named-only`.

- `undocumented`: no entry mentions it.
- `named-only`: mentioned, but the entry does not reach `located` for it. This covers a bare mention; an item the entry only mentions because its subject is another item; a mention on a line that names more than three items (distinct identifiers, plus numbers written as a list), because a list documents none of its members (the bit positions and fields of the entry's own subject, the callees it lists after a call word and the directory names of a path it writes are not counted: see Fields and bit positions and Citation); an entry with no citation of its own; an entry with a citation but no label; a row of a pointer table that no entry of its own describes; an index file (`AGENTS.md`, `README.md`, `IRIX_FILES.md`, `docs/coverage.md`, `docs/open-questions.md`); a committed table; and a fenced listing.
- `located`: the entry carries a citation of its own and says the item's role or effect is `unknown` or hedges it (below), and gives where the item is (an address, offset or size, records, callers or sites). Identity and location are established, what it does is not. A subject whose entry is templated (below) is at most this, and so is a pointer-table row whose entry holds 0.
- `understood`: the entry has a label (`established` or `inferred`), at least six plain words that do not restate its subject's name, at least two items stated about the subject (numbers or code names other than its own and its row's address; in a data table, each value cell, see Data tables), a citation of its own, no hedge anywhere in it, and no `unknown` about its role or effect. An `unknown` about a sub-fact does not demote it (see Open sub-facts). The words are not read for meaning: check the cited section.
- `no-software-dependency`: the paragraph says "no shipped software or published source" depends on the fact (`AGENTS.md` section 6) and names the routes tried (the word "routes" or "tried"). The row is finished. Like every other status it goes to the entry's subject only.

A row is done when it is `understood` or `no-software-dependency`. The repository is finished when every row of every table is done.

### Subject

An entry credits one item, its subject:

- a table row: the first identifier in the first cell that holds one. An identifier is a backticked span, a code-like word (an underscore, a digit or an inner capital) or a hex number. A plain decimal counts only in a column headed ioctl, entry, record, routine, slot or request, so that a row-number column is skipped. The header row has no subject;
- a list item or paragraph: the identifier it starts with, after any bullet and emphasis. When it starts with prose, the first identifier of the heading above it;
- a header definition: the name it defines and its value, for the comment above it and the one beside it. A comment on a line of its own has no subject.

Every other identifier, number or file name in the entry is a mention and stays `named-only`. One exception: a command word stored to a register is a pair, so the entry whose subject is the register credits the word it states.

### Citation

A derivation citation must tie the entry to its own item. Each of these counts, and none counts when it is the subject itself:

- an offset (`+0x1a4`, "offset 0x40"), or a hex address after "address", "at", "entry", "record" or `@`. A table row's own address, slot or index cell is its identity, not a derivation: a number that is the row's own cell (or its low 20 bits) does not count, only a different location does;
- a callee or caller written in code (`calls`, `calling`, `called from` or `called by` followed by a backticked name; every name of a list such as ``calls `a`, `b` and `c` `` counts, and none of them is an extra item on the line);
- a source file or a path with at least two slashes (the Odyssey kernel driver initialization source unit, `libglcore/asm/ODYSSEY/x.s`);
- a binary or object file name (`odsy.o`, `libGLcore.so`) together with a backticked routine of it other than the subject.

A release or patch number (`6.5.30m`, `patch 4103`), a binary name alone, and a link to another page are not citations: every item of a build shares them.

### Hedges and restated names

An entry that closes with the label `Unverified.` (where others close with `Inferred.` or `Established.`) grades at most `located`, whatever else it says. It marks a batch of entries written quickly and not yet re-read against the binary or the source, so that the understood count includes only what has been checked. The cap applies to the closing label alone, as the last words of the entry or of a table row's last cell; `Unverified` in the middle of an entry reads as a hedge, as below. Re-reading an entry means correcting it and replacing the label with `Established.` or `Inferred.`.

An entry that says what it did not derive is not a derivation. "Not derived", "not shown", "not determined", "not known", "not established", "not decoded", "unidentified", "unclear", "guess", "presumably", "speculative", "assumed", "named for", "named after", "from the name", "from its labels", "name only" and "name-derived" demote an entry to at most `located`, as `unknown` does (`HEDGE` in the script). A hedge about the entry's own subject is meant; write the behaviour you did derive in a sentence of its own and leave the hedged part out.

The plain words of a role sentence do not count when they come from the subject's name. The identifier is split at underscores and case (`mClearEram` is `m`, `clear`, `eram`); a word of prose that is one of those parts, an inflection of one (`clears`), or the word an abbreviation stands for (`exp`, `exponential`) is dropped before the count of six. "Clears external memory" for `mClearEram` has one word of its own.

### Fields and bit positions

A line that names more than three items documents none of them, but the bit positions and fields of the entry's own subject are part of describing it, not extra items. For an entry that has a subject, a list that `bit`, `bits`, `bit positions`, `field` or `fields` introduces is not counted when it holds nothing but numbers or bit ranges (`bits 3, 5, 7 and 9`, `bits 31:28`) or field names, each with at most its own bit range (``fields `EN` [0], `MODE` [3:1], `BUSY` [7]``). A field name is a backticked name or a code-like word. Any other identifier on the line still counts, and a list that mixes in a name that is not a field of the subject, or has no subject, is counted as before. The fields stay items stated about the subject for the two-item minimum.

### Open sub-facts

An entry that states its role and effect, labelled established or inferred, may say that a sub-fact is `unknown` (which of three identical groups serves which source, what one field holds) and stay understood. The test is mechanical: take out every sentence (or table cell) that says `unknown`; if what is left still has a label, six role words that do not restate the name, two items stated about the subject and a citation of its own, the entry is understood. It is also counted in `understood_with_open`. Put each open sub-fact in a sentence of its own, with the route that would settle it, so the rest of the entry does not depend on it.

The entry is demoted to `located` when the `unknown` sentence is about the role itself: it names the role, effect, purpose, function, behaviour, meaning or semantics, or says what the item does, is for or means. Hedges (below) still demote the whole entry. The grader reads words, not meaning, so an entry whose role is really the open fact can still pass: the audits catch that.

### Templated entries

Mask the identifiers, file names, numbers and punctuation of an entry and lower-case what is left: that is its sentence skeleton. The cap applies to each sentence, not to the entry. An entry is split into its sentences (each table cell, then each sentence in it) and a sentence that has three plain words or more is masked the same way. For the cap the type and count words a generated frame varies between rows are masked too (signed, unsigned, byte, short, integer, float, double and the number words one to sixteen), so "from three signed bytes" and "from four unsigned shorts" are one sentence. When more than 5 entries (`TEMPLATE_CAP` in the script) contain a sentence with one skeleton, counting table rows, list items, paragraphs and header comments across every document read, that sentence is a template. An entry grades at most `located` when most of its sentences are templates, or when the role words of the sentences that are not templates are fewer than six: a shared sentence added to a unique one earns nothing for the entry. The sentence that says no software depends on a fact is counted separately, and caps only a no-software-dependency status. One sentence pattern repeated over many names is bulk, not a separate derivation for each. `summary.tsv` counts the rows this capped in `templated`. Two entries that differ by a word of prose have different skeletons, so the cap catches mechanical repetition, not paraphrase; read the `understood_distinct` column for that.

The sentence that says how the entry was derived (what it was read against, matched to, compared with or generated from: `read in full`, `read against`, `matched`, `holds the same routine`, `same number of calls`, `generated from`, `compared with`, `derived from`, `disassembly`) is judged on its own. When its skeleton is a template the entry grades at most `located` whatever its other sentences say: a unique role sentence beside a shared evidence sentence does not make the evidence the entry's own, and the evidence is the part that has to come from this binary.

### Data tables

A row of a structured data table is one whose cells are mostly values: at least two of its cells (`MIN_DATA`) hold a decoded value and they are at least half of the cells that are not empty. A cell is a value when it is short (at most five words) and holds a digit or a code span: a pure integer or hex number, `1280x1024`, `20 states`, `table at 0x2bdc`. Each value cell is one item stated about the row's subject, whether or not another cell holds the same number. Two kinds of cell give no item: the subject's own cell, and a column headed address, offset, slot, index, entry, record, routine, ioctl, request, row, number or `#`, which says where the row is. A row with a sentence of its own around the values is graded by the ordinary rules, except that its pure-integer cells are items.

The template cap compares a short cell of such a row (five words or fewer) whole, as written, not by its skeleton: repeated labels around different values (`writes register 0x2300`, `writes register 0x2304`) are not one sentence repeated, but the same cell word for word in more than 5 entries (`prints payload, then hangs`) is a template like any other sentence. A row's short cells still give their role words. A table that does not state a value per row is not a data table, so a prose column cannot borrow the rule. A pure integer in any other table is still the row's own address, slot or index, and gives no item.

### Pointer tables

A row of a table that points at something (a dispatch entry that holds a handler address, a command that names a handler, an entry that holds a program address) says where the pointer is, not what its target computes. It is not credited by its target's entry. It earns a status only from an entry whose subject is the row's own number (the slot, entry or command number) and that names the table's program or the target; without one it is `named-only` when its target is mentioned and `undocumented` when it is not, except that an entry that holds 0 points nowhere and is `located`. The config marks such tables with `"pointer": true` (a `u16-table` is always one).

### Namespaces

A bare number is matched only in the chapters of its own table. A register window whose config lists no documents ignores the chapters `tokens.docs` lists, and tokens ignore the chapters the windows list, so the block id 0x004 written in a token chapter does not describe the register at offset 0x4. Name the token chapters in `tokens.docs` and the register chapters in each window's `docs` when one document set would otherwise serve both.

### Truncated tables

A `limit` in the config that reads fewer entries than the file holds is reported: `summary.tsv` has a `truncated` column on the table (`geif.u: 512 of 1024 entries`), the script prints a warning, and `docs/coverage.md` says the table was read in part. Prefer no `limit`.

### Files matched by path

A row of `binaries.tsv` is credited by the path an entry writes, not by the file name. An entry's path counts when it is the row's install path from any directory down (`usr/gfx/ucode/KONA/dg4/vfo/1280x1024_60.vfo`, or after `root/`), or for an archive member the member after the archive (`gfxs.a(gfx_flow.o)`) or alone, and when it names that file and no other. A bare name that two files with different content share (`1280x1024_60.vfo` in `usr/diags/IR/data/` and in `dg4/vfo/`, `gfx.o` in `IP27boot` and `IP35boot`) names neither, so write the directory. Byte-identical copies are one row and share the credit. Naming an archive does not credit its members.

### Builds of one function

A function row exists once per binary. When a name is defined with different code in several binaries, an entry credits it only in the binary the entry names: by its path as `binaries.tsv` spells it, from any directory down (`usr/gfx/arch/IP32CRM/libGLcore.so`, or just `libGLcore.so` when no other binary has that name), or for an archive member by `gfxs.a(gfx_flow.o)` or the member alone. The name must pick out one binary: a path that matches several builds with different code names none of them. Builds with the same `code_sha` for that name have the same code and share the credit. Every other build is at most `located`. A name that has the same code wherever it is defined needs no citation of a binary. `summary.tsv` has one row, `functions in <binary>`, per binary with functions.

### Identification by match alone

An entry that identifies its item only by matching it to a public routine (matched by name, size or number of calls, a comparable or similar size, "the specification this routine is generated from") and does not say it read the body ("read in full", "read end to end", "read against", "read from the body", "the whole body") grades at most `located`, unless it states a datum of this build: an offset (`+0x1a4`, "offset 3756"), an immediate value ("constant 0x7f", "literal 1.0", "opcode 2") or the address of a callee ("calls `foo` at 0xd9bb240"). The routine's own address and size are the row's identity, not such a datum. A match shows that a public routine has the same name and shape; it does not show what the shipped body does. The words are `MATCH_ONLY`, `BODY_READ` and `BUILD_DATUM` in the script.

### Cross-workspace role check

The InfiniteReality, Odyssey and CRIME workspaces share much of the OpenGL sample-implementation code, so one role sentence can be copied from one workspace into another. An understood entry whose subject is a function with the same name as an entry in a sibling workspace, whose role clause is identical to the sibling's or at least 90% alike after identifiers, numbers and case are masked, and that states no datum of its own build (above), grades at most `located`: the text is the sibling's, and nothing shows it was checked against this binary. The role clause is the text after the heading (`` `name` in path: ``) up to the first semicolon or sentence end, before "and it occupies". The check is symmetric, so both workspaces lose the credit.

The siblings are the config's `siblings` (`{name: path from the repository root}`); `--sibling NAME=PATH` selects another checkout. Only a sibling's documents are read, with its own config, never its tables, and as they were at the commit recorded in `scripts/inventory-siblings.json`, so the result does not depend on the order the workspaces are regenerated in or on what the sibling's checkout holds (see Reproducible runs). A sibling that cannot be found, or is of this workspace's own family, fails the run. `--skip-siblings` skips the check, says `skipped` in `summary.tsv` and the `coverage.md` headline, and gives tables that are not comparable with a run that found them. `summary.tsv` counts the rows this capped in `reused`.

### Function rows the generator rejects

A function row stands for one function, so its name has to pick one out. When its name is defined at more than one address in the binary (a name defined in several compilation units, such as a generic routine and a board's own copy of it), the row is the lowest definition, and only an entry that writes an address inside that function (its start or an instruction in it, not a `+0x` offset) credits it; an entry that names it without such an address makes it at most `named-only`. When another name sits at its address (aliases and duplicates), a name alone cannot say which row a document means, so the row is at most `named-only` unless an entry's header gives its subject as one of the names at that address, writes that exact address (not an offset) and cites the row's binary (and archive member, if any). That address makes the entry unambiguous, and the aliases are the same bytes, so such an entry credits every name at the address, up to the status the entry earns with the template cap and the other demotes still applied. A mention of the name, or an entry at another address, leaves the row at most `named-only`. `functions.tsv` says which in `rejected`: `multi-unit`, `shared-address` or both joined by `+`. `summary.tsv` counts them separately in `multi_unit` and `shared_address` for `functions` and the per-binary rows (a row can be in both), and `coverage.md` repeats the totals. `address-unknown` rows are not counted as ambiguous: see Rows with no address.

### Function addresses

A function's address comes from one source per name, and `address_source` in `binaries.tsv` lists the sources a binary used. The ELF symbol tables come first (`symtab`, then `dynsym`). `mdebug` supplies names they lack, and `dwarf` supplies names that neither has.

DWARF can be out of date. If the library was relinked after its debug information was written, the code moved and DWARF's addresses are wrong (a `libGL.so` has `glXQueryVersion` at 0xd833278 in `.dynsym` and at 0xd80f0a0 in DWARF). The script treats a binary's DWARF as stale only when some name has DWARF addresses that share none with the addresses the symbol tables give that same name. A static function that is defined in several compilation units, where the symbol table keeps only one of them, does not show this: its DWARF addresses overlap the table's, and the file's other DWARF addresses stay in use.

When DWARF is stale, its addresses are dropped and the label says so with a suffix such as `dynsym+dwarf (dwarf addresses stale, dropped except sections ...)`, whose last words, in full in `binaries.tsv`, name the exception below. The exception is a function that fills a section by itself, such as `_init` in `.init`. Relinking did not move those sections, so DWARF's address, which is the section start, is kept (hence `+dwarf` in the label). Without that exception the label reads `dynsym (dwarf addresses stale, dropped)`. A name left with no address after this is covered below.

A name defined at several addresses in the chosen source takes the lowest and is rejected (above).

### Rows with no address

Some static functions have code in the binary, and a name in its debug information, but no source gives an address for them: the symbol tables omit them and DWARF is stale. The `functions.tsv` row for such a function has address 0x0 and `rejected` = `address-unknown`. Nothing can credit such a row by address, and a reading round cannot render it, so it is not open work. `summary.tsv` and `coverage.md` leave these rows out of every status count and the denominator, as they do out-of-scope rows, and report them in the `address_unknown` column and a line under the coverage table. Reading round target selection skips them. They become ordinary rows again when a source supplies an address.

### What understood means for each table

Every table uses the same entry test above, so what a row's entry has to state differs by what the row is. `understood` shows that an entry states the following for the row, with a derivation of its own. It does not show the entry is right: `audits.tsv` does.

- `binaries`: what the file is and the role it plays for this family, with where that was read.
- `functions`: the function's role and effect, in the build the entry names when builds differ.
- `mmio`: the register at this offset has a stated role and effect. Bits or fields that were not decoded can stay open.
- `tokens`: the token or command word has a stated meaning and effect on the host command stream.
- `ioctls`: the request has a stated handler effect.
- `ucode`: usually the routine's extent (address, size, records) and how the host selects it (its entry point, dispatch slot or command). That is structure, not what the routine computes. The `computes` column of `summary.tsv` counts the understood ucode rows that say more.
- `spec-registers`: the specification's register has a documented name and role.

`computes` is the ucode-only count of understood, uncapped rows whose entry describes an operation on data: arithmetic, conversion, packing or a decision (`computes`, `converts`, `multiplies`, `clamps`, `packs`, `compares` and similar; the list is `COMPUTES_OP` in the script). The words that restate the routine's inputs and outputs (`input`, `result`, `returns`) are not read at all, so a closing sentence that only says what goes in and comes out earns nothing. An entry must name inputs and outputs (`input`, `operand`, `argument`, `takes`, `consumes`; `output`, `result`, `returns`, `produces`, `yields`), but those words alone earn nothing. An entry that says it does no arithmetic or computes nothing is not counted, and an entry whose opening clause says it copies, moves, stores, loads or dispatches words needs two different operation words after that clause, because one is usually address or counter bookkeeping. The test still reads words, not meaning; it can miss an entry that says the same thing differently, and an entry that uses operation words can still be wrong. The audit in `audits.tsv` grades what the entries claim, not this count.

### Scope

A group such as a whole kernel object or the generic X server holds mostly code that has nothing to do with the graphics hardware, and counting it whole hides the graphics share. The config's optional `scope` list takes function rows out of the counts by explicit rule:

    {"binaries": ["usr/x/Xserver"], "reason": "one line", "names": ["exact_name"], "patterns": ["regex.*"]}

`binaries` are globs on a binary's path as `binaries.tsv` spells it, or on the path of a byte-identical copy. A function is out of scope only when its name is in `names` or fully matches a regex of `patterns` in a rule that names its binary, and the rule says why in `reason`. Nothing is inferred from what the documents say about a function. The first rule that matches takes the row.

- The excluded rows stay in `functions.tsv`, graded as usual, with `scope` = `out:N`. `summary.tsv` reports them in `out_of_scope` and the `coverage.md` headline in its `Out of scope` column, with a table of the rules, their row counts and their reasons, so the excluded count is never hidden. `rows` and the percentages are over the in-scope rows only.
- The run fails, and writes nothing, when a rule has no reason, no names and no patterns, or no binaries; when a name or pattern matches no function of its binaries (a stale rule); or when it would exclude a function that reaches a register window, a token or an ioctl. Reaching means a resolved access site in a configured window, an access whose offset could not be traced, a token store or an ioctl compare, send or dispatch-table handler found by the scan. Such a function stays in scope.
- Exclude only code that is clearly not about the graphics hardware. A rule that lists what a subsystem is called is a claim by name, so keep it narrow and check what it matches.

### Distinct counts

`understood_distinct` in `summary.tsv` is the number of different sentence skeletons behind a table's understood rows. A table whose understood rows rest on few skeletons is templated bulk even when no skeleton is over the cap.

How a mention is found:

- Names: an identifier in backticks or a code block, any identifier that looks like code (an underscore, a digit or an inner capital) anywhere in a line, and any identifier in a header. A short or all-lower-case name (`save`, `window`) also reads as English, so for those only backticks, code blocks, header code and the call form `name()` count. Write the name exactly as the binary spells it.
- Register offsets: a header definition of the value, `+0xOFFSET`, the full physical address, or a bare hex value on a line or under a heading that says what it is (register, offset, field, FIFO, command and so on), in the docs the config lists for that window. A register a specification table names, whose name is documented, takes that status for the offsets inside it.
- Decimal numbers: a context word (the config's list, or for ioctls "ioctl") within the three words before the number or the one after it, or, for a table cell holding only the number, in the column heading. A number elsewhere on the line, or in the section heading, does not count.
- Tokens and words: the token's names; for a word stored to a register, its value within two lines of the register's offset or name; for other words, the value on a line or under a heading that says what it is.
- Ioctls: the handler names, and the number (decimal, or hex) in the config's ioctl docs on a line or under a heading that mentions ioctls.
- Microcode: the symbol or label; a routine that has no name, by its record number with "entry", "routine" or "record" next to it, as above.

The status measures what an entry claims and cites, not whether it is right: read the cited section. Generated listings, disassembly and verbatim dumps of a binary's own tables restate the binary and are not read.

## How register accesses are found

Each function of every ELF file in scope is disassembled and replayed over its basic blocks to a fixed point. A register or a stack slot keeps a value across a join only when every path into the join agrees (a block that nothing reaches and that is a single instruction, a nop pad or a copy of a branch's delay slot, is left out of the join; a larger unreached block, a switch target, starts with nothing known); when the paths agree on the window but not the offset, it keeps the window with an untraced offset. A frame pointer set to the stack pointer plus a constant addresses the same stack slots as the stack pointer. Constants are followed through `lui`, `ori`, `addiu`, shifts, adds and loads from read-only data, literal pools and the GOT. A value becomes a register window base when the config says so:

- `constant`: an address in a fixed range (a physical window, a kernel segment address of one, or a fixed user mapping);
- `field`: a load from a given displacement, the pointer field a structure keeps the base in;
- `global`: a load from a given offset of a named global;
- `argument`: a register on entry to a named function;
- `chain`: a record reached through an array of per-owner pointers. A load at `array_disp` gives the array, a slot number loaded at `index_disp` (any base register) and scaled by the word size is added, the owner's record is loaded from the slot at displacement 0, and each configured `fields` entry (a displacement into that record) is a window base. The slot number is checked, so a record of another owner in the same array type is not mistaken for the window;
- `return`: the value a named function returns.

The replay then learns two more sources inside each file: a function whose every call site passes the same window in an argument register starts with it, and a call to a function that always returns a window base yields it. An accessor (a function that takes a register address in an argument) counts as an access at that address.

A load or store through a window base is a site. When its offset is a constant it is a row of `mmio.tsv`; when the base is a window but the offset could not be traced (an index, a loop counter, a value passed in from elsewhere) it is counted as unresolved, per binary and window, and the headline in `coverage.md` gives the share. A loop's first iteration still yields its offsets, and the site is counted as unresolved as well, since the later iterations are not placed.

## What the scan does not see

- An access through a pointer the config does not name, and that is not passed in or returned by a function in the same file, is neither a row nor an unresolved site. A register window reached that way is missing from the count altogether, so add the pointer to the config when a reader finds it.
- Calls through function pointers are not followed, so an ioctl sent that way is missed.
- Functions that no symbol table names (stripped local functions) have no row in `functions.tsv`; a stripped binary's code is still scanned, in pieces between its exported symbols.
- Token words built from variables are not rows.
