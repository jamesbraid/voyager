## Host attachment

The attach path read so far is in [kernel-attach.md](kernel-attach.md).

- [software-now] **Which bridge and topology the Onyx4 graphics board uses.** `vga_check_for_pic` accepts a PIC (part 0xd102 or 0xd112) or an XBridge (0xd002), and `fglrx_attach` has two mapping paths: card directly on the bridge's bus (BARs through the bridge's per-device windows) or one connection point further away (BARs as PCI memory addresses through a PIO map), which reads like a card behind a PCI-to-PCI bridge. Read since: the Onyx4 user's guide (007-4634-002) puts two pipes in each G2-brick (XIO to the host) or G2N-brick (NUMAlink, with a node board), numbers them even and odd, and gives the first pipe the X bus identifier PCI:2:0:0 ([kernel-attach.md](kernel-attach.md#bus-and-bridge)). Also read since ([kernel-attach.md](kernel-attach.md#the-pipe-list-gfxsaklconfigo)): the kernel's own walker of the configuration table accepts a graphics card on either bus of a PIC (it keys a flag on the component's part number 0xd102 or 0xd112, the PIC's two bus part numbers in the public Linux 2.6.5 `pic.h`), numbers device slots 0 to 7, and adds 0x800000 to the bus address for the second bus. That makes a PIC-fronted slot **established** as a case the kernel handles; it does not say which brick uses it. Still open: which bridge part each brick carries and which mapping path a pipe takes. Tried: `fglrx_attach`, `vga_check_for_pic`, `vga_map_board_regions` in full; the user's guide. Next: search public newsgroup and mailing-list archives for `hinv -v` or `/hw` output from an Onyx4 (route 5); in software, read what `pciio_ppb.o` attaches to. If no published listing exists, this falls to hardware-only and is recorded there.
- [software-now] **The PCI bus clock and width.** Settled for software, see [kernel-attach.md](kernel-attach.md#bus-and-bridge) (the hardware half stays open): neither `fglrx.o` nor `vga.a` reads or sets them, and the bridge code only reads the speed field (bits 5:4 of the widget control register) and the PCI-X active bit (bit 33 of the widget status register) back into its soft state; no code read writes the speed field. Read since: the Onyx4 user's guide (007-4634-002) gives bus clocks (33 or 66 MHz, set by the slowest card on the bus) only for the host's PCI cards, and the XIO link rate (800 MB/s each way), and nothing for the graphics pipes. Still open, and hardware-only: the clock and width of the bus behind each graphics pipe. The test that settles it: read the bridge's widget control register (offset 0x20, bits 5:4) and status register (offset 0x8, bits 35:33) on a running Onyx4, or a published `hinv -v` / `/hw` bus-speed line for a graphics pipe. Not scheduled; the Onyx4 porting guide has no public URL in the sources index, and if one is found it can settle the value from documentation.
- [software-now] **Bridge device-register values for legacy I/O and frame-buffer access.** `vga_setbridge_to_legacy_io` and `vga_setbridge_to_lfb` write two values (VGA record +64 and +72) to the slot's Device(n) register. Established since ([kernel-attach.md](kernel-attach.md#the-pipe-list-gfxsaklconfigo)): `vga_earlyinit` copies them unchanged from pipe +0x70 and +0x80, and no kernel routine computes either. The configuration-table walker that builds the pipe list sets both to zero for a card it finds itself (`find_vga_noprom_pipe`), and leaves them alone for a component the PROM supplied, so in the PROM case the PROM wrote them. The public Bridge Device(n) layout (`bridge.h`, Linux 2.6.5, URL in sources/INDEX.md) puts bit 12 as the I/O-or-memory select, bit 13 as the device byte swap, bits 11:0 as the offset of the 1 MB window (address bits 31:20), and bits 28:14 as the prefetch, barrier, coherency, direct-map and error-lock controls; so, **inferred**, the two values are expected to differ at least in bit 12 and in the offset field. Still open: the two actual values. Next (the test that settles it): the PROM code that fills the graphics component in `ip35prom.img` (the failure string `init_klcfg_vgagfx` is at file offset 0x7f428; the routine that references it is not yet located, because the code's link address is not known), or a published dump of the Onyx4's klconfig / `/hw` graphics record.
- [software-now] **Byte swapping, in full.** Established: BAR 1, the ROM, the legacy I/O window and the VGA memory window are mapped with `PCIIO_BYTE_STREAM`, BARs 0 and 2 with `PCIIO_WORD_VALUES`; the VGA layer sets the bridge's `BRIDGE_CTRL_MEM_SWAP` for the console pipe's frame buffer and clears it again when it unmaps; the kernel's DMA buffers are mapped with the flag word 0x2022, whose effect on the bridge's DMA byte swap is not established (the DMA-address routine of `pcibr.o` would settle it); and `fglrx.o` never touches a bridge swap control ([kernel-attach.md](kernel-attach.md#bus-and-bridge)). Still open: the value of `BUF_SWAP` in `CP_RB_CNTL`: the only sites of `fglrx_drv.so` that touch offset 0x704 with a followed constant base are `r200_RegisterRingBufferLocation` and `r200_EnableRPTRwriteback`, and the first keeps the field, so the value is whatever the card had before, which the option ROM's register scripts and the reset state decide. Next: the register scripts of the three option ROMs for any write to 0x704 (option-roms.md), then the reset value in the R5xx acceleration guide's `CP_RB_CNTL` table; and the ring map's creation in `fglrx_drv.so` to confirm it comes from `fglrx_irix_kern_addmap`.
- [software-now] **Whether the IP35 PROM runs the option ROM.** The kernel runs it itself in `vga_init_board` (`xf86ExecX86int10`) for a card that is not the console pipe, and `vga_attach` skips it for the console pipe: it returns right after `hub_setup_prb` when board +0 is nonzero, and `vga_earlyinit` takes the console pipe's I/O window, frame-buffer address and bridge values from a record the PROM supplies ([kernel-attach.md](kernel-attach.md#the-pipe-list-gfxsaklconfigo)). **Established:** `vga_attach` does not run it for the console pipe, and the first pass of `vga_earlyinit` (route A) registers the console board from the PROM's record without running it; the second pass (route B) does call `vga_init_board(board, 1)` for a console board, so the kernel runs the ROM there. **Inferred:** the PROM sets that card up before the kernel starts, because the kernel refuses a console pipe whose "inited" byte (+0x57) is zero and no kernel routine sets the byte. Still open: whether the PROM does so by running the option ROM. Checked: a string search of `ip35prom.img` finds `init_klcfg_vgagfx` and no string naming x86 emulation, a BIOS interrupt, an option ROM, VGA or ATI; the image is plain MIPS code with strings up to file offset about 0x6fa78 and about 0x80000 to 0x100000 is high-entropy (about 7.8 to 7.96 bits a byte), which may be compressed code. The next test: find the load address of the plain segments (the segment table starts at file offset 0x90; the reset code at 0x1400 is at 0xbfc00400), locate the code that builds the graphics component by its reference to the failure string, and read what it writes; if it only reads the card's registers or an expansion-ROM pointer from configuration space and never executes the ROM, the ROM is not run by the PROM. A published PROM console log of an Onyx4 boot (route 5) would also settle it.
