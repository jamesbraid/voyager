# X video driver: overlay, timing, stereo and BIOS-interface routines

`usr/X11R6/lib/modules/drivers/fglrx_drv.so` is the XFree86 video driver for the FireGL cards: an N32 shared object whose exported routine names and addresses come from its dynamic symbol table. This chapter has one entry per routine for the video-overlay, TV-timing, stereo and BIOS-interface code. Every routine starts from the screen record (argument a0): the word at +248 is the driver record, and the word at +48 of the driver record is the mapped register aperture. Register offsets below are byte offsets from that aperture; their public names are in [registers.md](../../evidence/registers.md).

Two helpers recur. The word-sized TV register window is read and written through two routines without exported names. `sub_43ffc0` (a0 screen, a1 index, a2 data) stores `a2 & 0x0fffffff` to the register at 0x844, stores `a1 & 0x1ff` to 0x848, stores the same value with bit 14 set to 0x848, polls 0x848 until bit 15 is set or a counter reaches 100, and stores zero to 0x848. `sub_440040` (a0 screen, a1 index) is its reader: it replaces the low nine bits of 0x848 with `a1 & 0x1ff`, stores that with bit 12 set, polls 0x848 until bit 13 is set or a counter reaches 100, stores zero to 0x848 and returns the word read from 0x840.

The overlay lock helpers are `sub_43a4c0` and `sub_43a540` (both take a0 screen). `sub_43a4c0` sets bit 0 of the register at 0x410, then, if bit 3 of 0x410 is clear, calls `FGLMDelay` (at 0x424640, through the global-offset-table word at gp-30836) with 10 and re-reads until bit 3 is set; it has no counter. `sub_43a540` clears bit 0 of 0x410 and sets bit 1 of 0x5c with a read-modify-write.

## Stereo and clock set-up

- `QBS_EnableStereo` (`fglrx_drv.so`, 80 bytes at address 0x43f440): **Established.**
  Takes the screen record in a0 and an on/off flag in a1, and returns nothing. It changes only the register at 0x228 (the aperture word at +552) and keeps a copy of the value it wrote in the driver record word at +3512, stored in the delay slot of the return.
  When a1 is nonzero it clears bits 19 and 18 (the mask 0xfff3ffff), ORs in the driver record word at +9212 shifted left 18, and writes the result.
  When a1 is zero it clears bits 20 to 17 (the mask 0xffe1ffff) and writes the result.
  The public headers define only bit 15 of this register, so what bits 20 to 17 mean on this board is unknown; the same four bits are the ones `R6TMDSTransmitLinux` sets (see below). Settling test: find every store of the driver word at +9212 (the two-bit field this routine shifts into bits 19 and 18) and every caller of this routine with `retools/tools/hostfacts.py`, and read the constants and conditions behind them; a value set that tracks a stereo or transmitter mode option would name the field (inferred). The register's layout for this chip needs the vendor reference; a public header that defines only bit 15 cannot.
- `QBS_FinishInit` (`fglrx_drv.so`, 196 bytes at address 0x43f1c0): **Established.**
  Takes a pointer in a0 to a word holding a screen number. It finds the screen record in `xf86Screens` (the global-offset-table word at gp-31764) and reaches the aperture as above.
  It loops until the register at 0x8 (the PLL index register) reads, with bit 6 masked off, as 0x88: while it does not, it stores the byte 0x88 at +11 and reads again. There is no counter. The value 0x88 is PLL index 8 with the write-enable bit 7 set.
  It then calls `R200INPLL` (the slot at gp-30896, address 0x410dc0) with index 8, which stores the index byte and returns the data word at +12, and stores that word ANDed with 0xfffffcff (bits 9 and 8 cleared) to +12. The store sits in the delay slot of the next call.
  Last it calls `QBS_EnableOverlay` (the slot at gp-30688, address 0x43f0c0) with a1 = 1 and returns its result.
  Public headers list PLL index 8 as `VCLK_ECP_CNTL`, which defines bits 7, 6 and 1 to 0 only. What bits 9 and 8 of it select on this board is an open sub-fact: unknown. Settling test: look up PLL index 8 in the AMD register reference for the later R5xx part and in Linux's `radeon_reg.h` for a field at bits 9 and 8; a match in the layout makes the name inferred, and only a vendor reference for this chip makes it established. Separately, find the other writers of PLL index 8 in `fglrx_drv.so` and the option ROM images (the ROM's PLL script interpreter reads index 8 lane 0 only) to see whether any sets bits 9 and 8 to a nonzero value.
- `R6TMDSTransmitLinux` (`fglrx_drv.so`, 580 bytes at address 0x445480): **Established.**
  Arguments by register: a0 screen, a1 a 28-bit value or -1, a2 a divisor, a3 a four-bit value, a4 a two-bit value, a5 a flag. Returns nothing.
  Step 1, only when a5 is zero: the register at 0x3f8 (`CRTC2_GEN_CNTL`) becomes `(v & 0xfdfff0ff) | 0x04800000` (clears bit 25 and bits 11 to 8, sets bits 26 and 23).
  Step 2: the register at 0x294 is read, masked with 0xffffcff0 and ORed with `a3 & 0xf`.
  Step 3, when a1 is -1: that value is stored to 0x294; if bit 20 or bit 17 of 0x228 is set it clears bits 20 to 17 (mask 0xffe1ffff); the frame target is the low 21 bits of 0x214 (`CRTC_CRNT_FRAME`) plus 2; the pause is 1000 / a2 (1000 when a2 is zero).
  Step 3, otherwise: 0x294 gets the value ORed with `(a4 << 12) & 0x3000`; 0x220 gets `(a1 & 0x0fffffff)` ORed with the old top four bits; 0x22c gets its low 11 bits copied to bits 26 to 16 (the mask 0xf800ffff); 0x228 gets 0x1e0000 ORed in when bit 20 or bit 17 is clear; the frame target is the low 21 bits of 0x214 plus 3; the pause is 2000 / a2 (2000 when a2 is zero).
  Step 4: a nonzero pause is passed to `FGLMDelay` (the slot at gp-30836), then divided by 10 on the first path and by 20 on the second to give the polling pause. The routine reads 0x214 until its low 21 bits reach the frame target, calling `FGLMDelay` with the polling pause between reads when that is nonzero.
  The register at 0x294 has no public name, so what a3 and a4 select is unknown.

## Overlay scaler

- `FIREGL_HideOverlay` (`fglrx_drv.so`, 136 bytes at address 0x43db80): **Established.**
  Takes the screen record in a0. It calls `sub_43a4c0` (overlay lock), reads `OV0_SCALE_CNTL` (0x420), clears bit 30 (the scaler enable) with the mask 0xbfffffff and writes it back. Then it stores zero to the driver record word at +8332 and the value just written to the word at +3420, the second in the delay slot of the call to `sub_43a540` (overlay unlock), and returns.
  The word at +8332 is the one `FIREGL_ShowOverlay` sets to 1 on entry, so it records whether the overlay is shown; the word at +3420 is the driver's copy of `OV0_SCALE_CNTL`, which `FIREGL_ShowOverlay` also stores.
- `FIREGL_ShowOverlay` (`fglrx_drv.so`, 1900 bytes at address 0x43df00): **Inferred.**
  Takes the screen record in a0 and the overlay source in a1 to a6: a1 and a2 are a position, a3 the width and a4 the height (the end corner written to 0x404 is `(a3 - 1) | ((a4 - 1) << 16)`), a5 a buffer offset and a6 a pitch. Most of the body was read in the disassembly (instructions 0x43df00 to 0x43e668, with the divisions and the table walk checked against the decompiler's output); the scaler-increment arithmetic is the least checked.
  Entry: it calls `xf86GetEntityPrivate` (the slot at gp-32072) with the first word of the record at screen +220 and the value of the global `gR200EntityIndex`, keeps the first word of the returned record, and stores 1 to the driver word at +8332.
  Chip codes 47 and 49 (the driver word at +160): if a3 is below the word at +356 or a4 below the word at +360, it calls `xf86DrvMsg` (level 7) twice with two messages about the overlay scaler and the panel's native mode, the second giving the two words; a3 is then limited to 1536.
  Colour key and blending: when the driver word at +9208 is zero it calls `sub_43d740` with the key 0xf81f, `sub_43d6c0` with 1 and `sub_43d700` with 0; otherwise `sub_43d800`, `sub_43d780` with 1 and `sub_43d7c0` with 0. `sub_43d740` and `sub_43d800` write the key-colour pair at 0x4e4 and 0x4e8; the other four read-modify-write the key control register at 0x4f4.
  Then it takes the overlay lock (`sub_43a4c0`), writes 0, 0x10000000, 0x10000000, 0, 0x1000, 0 to 0xd20 to 0xd34 (the six `OV0_LIN_TRANS` words), builds the scale-control value from `OV0_SCALE_CNTL` masked with 0x7ffff0ff plus 0x400 (or 0x600 when +9208 is nonzero) and polls bit 0 of 0x5c (`CRTC_STATUS`) with no counter until it is set; the poll is unrolled six times and loops back to its start.
  Register writes in order: 0x420 and the driver word at +3420 get that value with 0x4100000c ORed in; 0x470 has bits 9, 8, 5 and 4 cleared and bit 9 set; 0x4a0 gets 0xf ORed in; 0x474 gets 0xaaaaa; 0x400 and 0x404 (or 0x600 and 0x604 with bit 14 of 0x420 set, when the word at +120 is nonzero); the vertical increment 0x424 from the height ratio; 0x480 and 0x484 from `sub_43d840`, which scans four 36-byte records starting at 0x465d00 for a fit; 0x488, 0x48c, 0x428 and 0x42c from `sub_43da40`; 0x2090 in the driver record from the position and pitch; 0x494 as `min(x extent, 4095) | (min(a1, 15) << 16)`, 0 to 0x498 and 0x49c, `((a4 - 1) << 16) | 0xfff` to 0x430, `((a4 - 1) << 16) | 0x7ff` to 0x434, 0 to 0x4f8, bit 12 cleared in 0x420, the 0x2090 value to 0x440, 0 to 0x444 and 0x448, `((a6 >> 3) << 4) & 0xffff0` to 0x460, and 0x470 again with bits 19, 18 and 2 to 0 cleared and bit 6 flipped; 0x420 with bit 30 set and bit 5 set when the driver word at +9204 is nonzero, cleared when it is zero; and last 0x43c from the doubleword at +176 of the entity record. It then calls `sub_43a540` (unlock) and returns that call's result.
  The table walked for 0x494 starts at 0x465eb0 and has the number of 8-byte records held in the word at 0x467ed8; the first record whose first word is not below `(1 << d) << 16` (d is bits 9 and 8 of PLL register 8, read by `sub_43d680`) supplies the two byte fields, and the last record is used when none qualifies. The units of the increments written to 0x480 and 0x484 are unknown.

## TV timing

- `SaveTimingCode` (`fglrx_drv.so`, 208 bytes at address 0x4400c0): **Established.**
  Arguments: a0 screen, a1 an output record. It stores 0x80000680 to `TV_MASTER_CNTL` (0x800), reads the register back and keeps that value in the stack, not the value the register held before, and rewrites 0x800 as `(v & 0xffffffee) | 1` (bit 4 cleared, bit 0 set).
  It then reads the 111 indexes 401 to 511 with `sub_440040` and stores each word in the output record starting at +380, in index order, four bytes apiece. Finally it writes the kept value back to 0x800. It returns nothing.
- `RestoreTimingCode` (`fglrx_drv.so`, 240 bytes at address 0x4401c0): **Established.**
  Arguments: a0 screen, a1 the record `SaveTimingCode` filled. It reads 0x800 and keeps it, clears bit 31 of 0x8ac, stores 200 to 0x8ac (reading the register back after each store) and rewrites 0x800 as `(v & 0xffffffee) | 1`.
  It writes the 111 words at record +380 onward to the indexes 401 to 511 with `sub_43ffc0`, one index per word, then stores the kept value back to 0x800 and sets bit 31 of 0x8ac again. It returns nothing.
  Both routines take the same index range, so the saved block is exactly what the restore loop writes back.
- `Write_FIFO_Values` (`fglrx_drv.so`, 1176 bytes at address 0x4437c0): **Inferred.**
  Takes the screen record in a0 and returns nothing. It reads six lists from the global block at 0x469180 (the word at gp-32672, 0x470000, minus 28288), the same block `Set_MV_Mode` reads. Each list has a count word at +4 of its start and 8-byte pairs from +8, and the lists start at block +160 and are 404 bytes apart (the counts are at block +164, +568, +972, +1376, +1780 and +2184).
  Each 8-byte pair is packed as `(low & 0x3fff) | ((high & 0x3fff) << 14)` and written with `sub_43ffc0`. The loop counter advances by 2 a pass while the pair pointer advances by one pair, and runs while the counter is below the count rounded up to even, so a list is covered in half as many passes as its count. Lists one, three and five take the pair's first word as the high field; lists two, four and six take it as the low field.
  Before the lists it stores 0x80000680 to 0x800 (the same value `SaveTimingCode` uses), keeps the read-back value, sets `(v & 0xffffffee) | 1`, and writes 0x8ac as the word at 0x4681d4 ORed with the first start index masked to bits 23 to 16 and the second masked to bits 15 to 8. With h(n) = (n + 1) >> 1 for the counts n of lists one to six, the first start index is (509 - (h(n1) + h(n4) + h(n3) + h(n6))) >> 1 and the second is (510 - (h(n1) + h(n4))) >> 1, both taken as signed arithmetic shifts.
  Index runs: list one writes from index 511 downward; list two from `(the word at 0x4681d4 << 1) | 1` upward; list three from `second start << 1` downward; list four from `(second start << 1) | 1` upward; list five from `first start << 1` downward; list six from `(first start << 1) | 1` upward. The routine ends by restoring 0x800 to the kept value.
  Which registers the indexes 0 to 511 select through 0x844 and 0x848 is an open sub-fact: unknown. Other code fills the six lists. The access form is read: the routine `sub_43ffc0` is `OutTVFifo` in the binary's debug information, which stores the data word to 0x844 and a control word to 0x848, polls bit 13 of 0x848 until it is set (at most 100 reads) and clears 0x848; its partner `InTVFifo` (0x440040) stores to 0x848, polls the same bit, clears 0x848 and returns the word at 0x840 (**established**, `retools/tools/hostfacts.py` on both). So the indexes address an indirect store behind the TV block, not registers in the aperture. Settling test: look up `TV_HOST_WRITE_DATA`, `TV_HOST_READ_DATA` and `TV_HOST_RD_WT_CNTL` in the AMD register reference and Linux's `radeon_reg.h` for the layout of the 0x848 control word, and compare it with the words the two routines store; what each of the 512 indexes holds needs the TV encoder documentation, which this workspace does not have.
- `Set_MV_Mode` (`fglrx_drv.so`, 540 bytes at address 0x4441c0): **Established.**
  Takes the screen record in a0 and returns nothing. It keeps `TV_MASTER_CNTL` (0x800), sets bits 1 and 0, and calls `sub_443f80` with the mode word at driver record +192; that helper stores small constants into words 0 to 40 of the global block at 0x469180 (the word at gp-32672 minus 28288), chosen by that mode and by the word at +184.
  It then stores zero to 0x848 and writes the block's first five words to 0x87c as `w0 | w1<<2 | w2<<4 | w3<<6 | w4<<8`.
  The selector is the driver word at +184. Register 0x878 gets `(f << 6) | (g << 2)` with g = 7, f = 0 for selector 0, 2 or 5; g = 6, f = 1 for 1, 3 or 4; g = 0, f = 0 otherwise. Register 0x880 gets 0x4d8d382d for selector 0 or 2 (0x4d8d2d2d when the byte at +188 is nonzero), 0x4d8d3030 for 1 or 4, and 0x3f7f382d otherwise. Register 0x884 gets 0xb7da for selector 0 or 2, 0xb0cf for 1 or 4 and 0xb7cf otherwise.
  Then 0x85c becomes `(block word at +20 << 17) | (block word at +24 << 20) | (old & 0xffedffff)`, `sub_443e40` runs with the mode word, and 0x800 is restored.
  Only 0x85c has a public name on this list (`TV_Y_RISE_CNTL`); what the mode and selector words mean is unknown. Settling test: the shipped X module carries the `TVStandard` option strings (NTSC-M, NTSC-JPN, PAL-D, PAL-M, PAL-SCART and others); run `retools/tools/hostfacts.py` on the option-processing routine that references that string, find which constants it stores into the driver words at +184 and +192, and match each to its option string; that names the selector and mode values (inferred, from the option strings) without any register documentation.

## Chip-library start-up

- `R200LinuxCailInitCail` (`fglrx_drv.so`, 828 bytes at address 0x43ea80): **Established.**
  Takes the screen record in a0 and returns 1 on success and 0 on any failure.
  It calls the helper `sub_43ea00` twice. The helper calls `xf86ReadBIOS` (the global-offset-table word at 0x467740, dynamic symbol 432) with the driver word at +40, an offset, a buffer and a length of 2, and returns 1 only when the call returns exactly the requested length. The first read is at ROM offset 72 and gives a 16-bit value that is zero-extended into the word at driver +8548 (0x2164); the second is at that value plus 6 and is zero-extended into the word at +8552. If either read fails the routine returns 0 at once.
  It then fills a block that starts at driver record +8380 (size word 820, 0x334, stored first): the screen at +8388, 0 at +8668, the word at +12 copied to +8460, the word at +7800 to +8516, 2 at +8512, the word at +16 of the record at +4 to +8464, the chip code at +160 to +8468, the screen word +804 shifted left 10 to +8524 and +8504, 2 at +8528, the aperture at +8600, the word at +40 to +8596, `((aperture word at +224 >> 16) & 15) + 1` to +8492, the word at +44 of the record at +4 to +8496, 1 to +8688 and 0x80000 to +8668.
  When the byte at +89 is nonzero the chip code stored at +8468 is remapped: 47 becomes 48, 49 becomes 51 and 45 becomes 46.
  Chip codes other than 44, 45 and 52 set bit 23 of the flag word at +8664; code 8 sets bit 30; codes 47 and 49 zero +8668 and set bits 31 and 4. Otherwise +8604 is zeroed. The six callbacks are stored from global-offset-table words: read PCI config at +8396, write PCI config at +8400, get PCI bus data at +8404, set PCI bus data at +8408, read ROM image at +8412 and microsecond delay at +8416 (the slots at gp-32248, -32252, -32256, -32200, -32228 and -32204).
  It calls `CAILInitialize` (the slot at gp-31140) with the block's address. A nonzero result logs two errors (level 5), the second saying initialisation failed, and returns 0. A zero result logs the library version (level 7, the word at +8384), calls `xf86EnablePciBusMaster` with the entity record at +4 and 1, and calls `CAIL_ASICSetup` with the block. If that returns nonzero it logs an error with the code (level 5) and returns 0; otherwise it calls `CAILQueryVideoBiosInfo` with the block and the word at +8548 and returns 1.
  The meanings of the ROM offsets 72 and the +6 field, and of the individual block words, are unknown; they belong to the closed chip library.

## Chip code from the PCI device ID

- The device-identification code at 0x414ce4 to 0x414d88 in `fglrx_drv.so` (the dispatch tree through 0x415564 and the stubs it branches to; the debug names place it only by distance inside `R200MinBits`, so it is named here by address): **established** for the table, **inferred** for the chip-family names.
  It starts from the 16-bit PCI device ID, the word at driver record +12, and picks one leaf of a compare tree. Each leaf stores, relative to the driver record: the chip code at +160, a small integer at +180 (0, 2 or 3), a flag byte at +88 (1 for every recognised ID), a flag byte at +89 (set only for the IDs below marked mobile; the byte at +89 is cleared at 0x414cf0 before the tree) and a word at +7800 (64, 128 or 256). An ID that no leaf matches keeps code 0, +180 = 0, +88 = 0 and +7800 = 64 (0x4154d0 to 0x4154e4), and `FGLInitCP` then logs "unsupported ASIC".
  I derived the table by stepping the instructions of the tree for every device ID from 0 to 0xffff (a script over the disassembly, with the register at 0x414ce0 clear; the one branch on a later test, at 0x4155b0, needs that register nonzero and so was not exercised). The leaves, by code, with the family the public PCI ID list gives each ID (inferred from the ID alone):
  - code 8: 0x4242, 0x5148, 0x514c, 0x514d, 0x516c, 0x516d (R200: All-in-Wonder 8500 DV, FireGL 8800, Radeon 8500 and 9100);
  - code 44: 0x4144 to 0x4147, 0x4149, 0x414a, 0x4e44 to 0x4e47 (R300, including the FireGL X1 ID 0x4e47 and FireGL Z1 0x4147);
  - code 45: 0x4150 to 0x4152, 0x4154 to 0x4157, and 0x4e50 with the mobile flag (RV350, RV360);
  - code 47: 0x4964 to 0x4967, and 0x4c64 to 0x4c67 with the mobile flag (RV250);
  - code 49: 0x5960, 0x5961, 0x5964, and 0x5c61, 0x5c63 with the mobile flag (RV280);
  - code 52: 0x4148, 0x414b, 0x4e48 to 0x4e4b (R350 and R360, including the FireGL X2 ID 0x4e4b).
  IDs not named in any leaf, among them 0x4153 (RV350 Radeon 9550), fall through to code 0. The word at +7800 is 256 for the code-52 IDs and for 0x4147, 0x4149, 0x414a, 0x4e44, 0x4e45 and 0x4e47; 128 for 0x4144 to 0x4146, 0x4e46 and every code-45 ID; 64 for the codes 8, 47 and 49. The word at +180 is 2 for code 8 and 3 for every other recognised code. What +180 and +7800 mean is unknown. The mobile flag matches the remap in `R200LinuxCailInitCail` above (47 to 48, 49 to 51, 45 to 46).
  So the two cards of the Onyx4 map as follows: a FireGL X1 (0x4e47) gets code 44 and a FireGL X2 (0x4e4b) gets code 52; both are in the group that `PM4LoadMicroCode` serves with `aPM4_Microcode_R300` and that `FGLInitCP` serves with the 0x42bec0 filler. Codes 8, 47 and 49 are the R200, RV250 and RV280 parts and take `aPM4_Microcode_R6x`.

## Register readback

- `R200GetCRTCResetState` (`fglrx_drv.so`, 60 bytes at address 0x449540): **Established.**
  Takes a screen number in a0, looks the screen up in `xf86Screens` (the word at gp-31764 plus the number times four) and returns the word at aperture +80 (`CRTC_GEN_CNTL`) ANDed with 0xfdfeffff, which clears bit 25 (the CRTC enable) and bit 16 (the cursor enable). It writes nothing.
  The mask is the same one `fglrx_attach` applies in `fglrx.o`; here the value is returned for the caller to write back.
