# Open questions

## Triage

Of the 44 entries below, 39 are `software-now`, three are `missing-release-or-binary` and two are `hardware-only` (the ImageSync capture proposals). Six of them also carry a hardware-only residue, marked in the entry and recorded, not scheduled: the PCI bus clock, the display output, the ROM select, whether the SG2 board has an AGP-to-PCI bridge chip, R300 shader arithmetic against silicon, and the display controller's tiled fetch order.

The tags:

- `software-now`: a step the workspace can take now, from the shipped binaries in `root/`, the public references in [sources/INDEX.md](../references/documents/INDEX.md) or public archives. Public trees that a fresh clone leaves empty need a shallow `git submodule update --init --depth 1 NAME`.
- `missing-release-or-binary`: the answer needs a file or release that the install set in [references/irix-files.md](../references/irix-files.md) does not include.
- `hardware-only`: no software or published source can settle it. Recorded, not scheduled. The two ImageSync capture proposals are wholly in this class; the residues above are the parts of `software-now` entries that are.

## Host attachment

The attach path read so far is in [kernel-attach.md](../software/kernel/kernel-attach.md).

- [software-now] **Which bridge part and which pipe-to-bus assignment.** Answered at the software level in [onyx4-bus-attach.md](../software/kernel/onyx4-bus-attach.md): the card is a PCI function on a Bridge-family chip (PIC or XBridge), observed in public hinv captures (widget 10 on a G2, widget 15 on a G2N, `Bridge` rev 3), driven by IRIX as PCI with the AGP aperture parked. Still open: (a) whether a G2 carries a PIC or an XBridge (the PROM prints the generic word `Bridge`; the code makes a PIC inferred, [r300-kernel-topology.md](../software/kernel/r300-kernel-topology.md#widgets-and-the-pic)); (b) the pipe-to-bus assignment (inferred: one pipe per PIC bus); (c) answered: 0x56 and 0x30 are the CG-brick in two raw encodings (`l1_command.o`, [r300-kernel-topology.md](../software/kernel/r300-kernel-topology.md#the-io-brick-l1-type-check-answered)); still open is which brick type a G2 and a G2N each report; (d) whether the SG2 board has an AGP-to-PCI(-X) bridge chip (hardware-only). Tried: `fglrx_attach`, `vga_check_for_pic`, `vga_map_board_regions`, `pic_attach` in full; the user's guide (007-4634-002) and the porting guide (007-4297-001); public hinv captures. Next: read what `pciio_ppb.o` attaches to; the PROM's bridge set-up ([kernel-attach.md](../software/kernel/kernel-attach.md#the-ip35-proms-vga-bring-up-ip35promimg)).
- [software-now] **The PCI bus clock and width.** Settled for software, see [kernel-attach.md](../software/kernel/kernel-attach.md#bus-and-bridge) (the hardware half stays open): neither `fglrx.o` nor `vga.a` reads or sets them, and the bridge code only reads the speed field (bits 5:4 of the widget control register) and the PCI-X active bit (bit 33 of the widget status register) back into its soft state; no code read writes the speed field. Read since: the Onyx4 user's guide (007-4634-002) gives bus clocks (33 or 66 MHz, set by the slowest card on the bus) only for the host's PCI cards, and the XIO link rate (800 MB/s each way), and nothing for the graphics pipes. Still open, and hardware-only: the clock and width of the bus behind each graphics pipe. The test that settles it: read the bridge's widget control register (offset 0x20, bits 5:4) and status register (offset 0x8, bits 35:33) on a running Onyx4, or a published `hinv -v` / `/hw` bus-speed line for a graphics pipe. Not scheduled; the Onyx4 porting guide has no public URL in the sources index, and if one is found it can settle the value from documentation.
- [software-now] **Byte swapping, in full.** Established: BAR 1, the ROM, the legacy I/O window and the VGA memory window are mapped with `PCIIO_BYTE_STREAM`, BARs 0 and 2 with `PCIIO_WORD_VALUES`; the VGA layer sets the bridge's `BRIDGE_CTRL_MEM_SWAP` for the console pipe's frame buffer and clears it again when it unmaps; the kernel's DMA buffers are mapped with the flag word 0x2022, whose effect is now established in the 6.5.22 bridge objects: "clear byte swap", so Device register bit 19 stays 0 for the direct window and the translated and 64-bit paths carry swap in the address ([r300-kernel-dma.md](../software/kernel/r300-kernel-dma.md#the-bit-19-answer-in-full)); and `fglrx.o` never touches a bridge swap control ([kernel-attach.md](../software/kernel/kernel-attach.md#bus-and-bridge)). Established since: the two slot-register values the PROM supplies for the legacy I/O and linear frame-buffer windows both have bit 13 set, the device byte swap in the public Bridge layout ([kernel-attach.md](../software/kernel/kernel-attach.md#the-ip35-proms-vga-bring-up-ip35promimg)). Still open: the value of `BUF_SWAP` in `CP_RB_CNTL`: the only sites of `fglrx_drv.so` that touch offset 0x704 with a followed constant base are `r200_RegisterRingBufferLocation` and `r200_EnableRPTRwriteback`, and the first keeps the field, so the value is whatever the card had before, which the option ROM's register scripts and the reset state decide. Next: the register scripts of the three option ROMs for any write to 0x704 (option-roms.md), then the reset value in the R5xx acceleration guide's `CP_RB_CNTL` table; and the ring map's creation in `fglrx_drv.so` to confirm it comes from `fglrx_irix_kern_addmap`.
- [software-now] **What the PROM's graphics bring-up leaves unread.** Read in [ip35-prom-graphics.md](../software/firmware/ip35-prom-graphics.md): the creator of the graphics component (the node-PROM PCI scan, gated on the L1 brick type `V` or `0` in 6.5.30 only), BAR 0 and command-register assignment, the meaning of the lower-case brick types, only the console pipe being initialised, and the 6.5.22 equivalence. Still open: the order boards are linked (which head is pipe 0), how the L1 tells bricks apart for the type request, the XIO widget scan's link and ID-read routines, and the 6.211 patch image. Tried: decompiling both parts of the 6.5.22 and 6.5.30 images and the chain from the widget scan to the component creator. Next: the board-add routine and the L1 firmware's destination handling.

## Command processor and ring

- [software-now] **Ring parameters and order of CP start-up.** Settled: the kernel object never programs the ring base, size or microcode, see [kernel-attach.md](../software/kernel/kernel-attach.md#command-processor-microcode-and-memory-controller-in-the-kernel). The X server module does it ([kernel-attach.md](../software/kernel/kernel-attach.md#command-processor-start-up-x-server-module)): `PM4LoadMicroCode`, `r200_RegisterRingBufferLocation`, `r200_EnableCommonBusMaster`, `r200_SetPm4OperationMode` (mode 8, both queues bus-master), `r200_EnableRPTRwriteback`, `FGLEnableCP`, `FGLStartCP`. Answered since: `FGLInitCP` and the routine at 0x42bc00 are read ([x-driver-functions.md](../software/xsgi/x-driver-functions.md#command-processor-initialisation), [kernel-attach.md](../software/kernel/kernel-attach.md#command-processor-start-up-x-server-module)), and `firegl_cp_init` takes the ring from a map the X module created earlier, named by handle, not from `kmem_contig_reserve`. Settled: `firegl_cp_init` adopts three already-created memory maps, named by handle, see [kernel-attach.md](../software/kernel/kernel-attach.md#command-processor-microcode-and-memory-controller-in-the-kernel). Still open: how the X module creates that ring map and forms the bus address it keeps at E +0x48, and what the E fields at +0x18, +0x38 and +0x58 are before `FGLInitCP`. Next: the writers of those entity-record fields in `fglrx_drv.so`, and the map-creating calls (`firegl_AllocBuffer`) that precede the start-up.
- [software-now] **Fence: the time stamp.** The write-back registers are read ([kernel-attach.md](../software/kernel/kernel-attach.md#command-processor-start-up-x-server-module): `r200_EnableTimeStampWriteBack` sets `SCRATCH_ADDR` and `SCRATCH_UMSK`, `r200_WriteTimeStamp` writes the four scratch registers). Still open: the user-side half, the ATI time-stamp extension entry points and trackers in `fglrx_dri.so` and `fglrx_dri64.so` (`glSendTimestampATI`, `glWaitTimestampATI`, `__glATIWaitForTimestamp`, `__glATIQSTimeStampRetired` and the `__glATI*TimeStampTracker` routines), which are `located` or `named-only` in the inventory, and what the kernel or the chip does with the stamp. Next: read those routines against the scratch-register layout.

- [hardware-only] **How the combined swap-ready reaches the R300 flip.**
  Unknown: what makes the pipes of a swap group show their new frames together after the card's swap-ready sum completes. Tried: the kernel (`is1_fire_swapready`, `is1_release_swapready`, `is1_intr`),
  the X module (`SGIGLXSwapBarrierInit` and its callbacks), the DRI and GLX bind routines and `olsgsys`'s swap test ([r300-swap-framelock.md](../software/kernel/r300-swap-framelock.md)); no code writes a head
