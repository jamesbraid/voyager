# Option ROM x86 init, 6.5.22 images

What the init entry (offset 3) of the 6.5.22 `sg2.bin` and `sg3.bin` does, in the order it does it: the ports and registers it touches, the values it writes, and the script tables it interprets. It is written against the 6.5.30 account in [option-roms.md](../../software/ucode/option-roms.md#bios-code); the 6.5.22 init shares most routines with it, and this page says where it does not. Register scripts themselves are decoded in [init-scripts.md](init-scripts.md).

Grades are explained in [README.md](README.md#grades). Register names in the Linux column are the pinned `radeon_reg.h` names (**software expectation**); names marked "voyager" are the names of this repository's R300 display unit.

## Method

- **Listing and call graph.** The images were disassembled as 16-bit real-mode x86 in the project's analysis container: `objdump -m i8086 -M intel` for listings, and a recursive-descent walk (Capstone in 16-bit mode) from the init entry and from the entries of the video interrupt, VBE and vendor function tables to find every reachable routine. Ghidra was not used: the images are flat real-mode code with no symbols, and the listings and the walker were enough to read every routine named here. The walk reaches 113 routines from the init entry of sg2 6.5.22 (109 in sg3) and 475 and 472 once the interrupt tables are followed.
- **Model run.** To get the real order and values of every access (including the values the scripts produce through read-modify-write), the ROM's own code was also run under a real-mode x86 CPU emulation: the card's I/O window, the PCI configuration mechanism, the timer and the BIOS interrupt `0x1a` are answered by a small model in which the chip is a register file that returns what was last written (with the I2C status registers reading as ready), and every access is logged. This is **observed** under that model. It is model behaviour, not a hardware capture: it shows what the ROM writes and in which order when the chip answers like that, and says nothing about silicon. Every branch that depends on a read from a monitor, an I2C device or a bit that only real hardware would set takes the path the model's constant answers lead to; those parts are read statically instead and marked so.
- The register script tables were also checked against the model run: the run writes the entries of ASIC init 1, ASIC init 2 and init 4 in table order, and the PLL init and dynamic clock dwords in order (**observed**).

## How the chip is reached

**Established.** The same three access forms as 6.5.30: nothing is reached through memory addresses; the init uses the card's I/O BAR (configuration offset 0x14, base `P`): indexed access through `P+0` (index) and `P+4` (data), direct access to the first 256 registers at `P+offset`, and PLL access through `P+8` (index with bit 7 set) and `P+0xc` (data). The 6.5.22 code that implements them is shape-identical to the 6.5.30 routines (accessor and script-interpreter functions match instruction for instruction ignoring addresses). The base is validated before each use: the word at `P+0x2e` must equal the PCIR device ID, otherwise the ROM scans PCI configuration space (ports 0xcf8 and 0xcfc) from the stored bus, device and function for the vendor and device dword, and takes bits 15:8 of the BAR at offset 0x14 as the base. **Observed:** the first script (below) zeroes `P+0x2c`, which wipes that device-ID word, so each later base lookup goes through the configuration scan (two configuration reads per lookup in the model run); this is the same in 6.5.30.

## The init, in execution order (sg2, 6.5.22; entry 0x6e4)

Addresses are sg2 6.5.22; sg3 6.5.22 addresses are noted where they differ (entry 0x6e9).

1. **Entry (0x6e4 to 0x736).** **Established.** Pushes all registers. On the first call only (the word at `cs:[0x13e]` is zero) it stores AX, which holds the card's bus, device and function, at `cs:[0x13e]` and CS at `cs:[0x140]`. It reads the word at configuration offset 0x14 with `int 0x1a` AX=0xb109; the low two bits are cleared; if the result is zero it writes 0xf000 back (AX=0xb10c) so the I/O BAR gets an address. It stores the result at `cs:[0x142]` and then writes three words through the I/O window: CS to `P+0x14` (the low half of `BIOS_1_SCRATCH`), the bus/device/function to `P+0x16` (its high half) and the device ID word at ROM 0x19a to `P+0x2e` (the high half of `BIOS_7_SCRATCH`). **Observed** with the model (BAR value 0x401, function 0x0800): `P` = 0x400, `P+0x14` = 0xc000, `P+0x16` = 0x0800, `P+0x2e` = 0x4e47.
2. **RAM-copy test and stack switch (0x738 to 0x762).** **Established.** Stores 0x1234 at `cs:[0x6941]` and tests that it reads back (true only if the ROM runs from RAM); if so it saves SS, SP and AX at `cs:[0x6945]`, `cs:[0x6947]` and `cs:[0x6943]` and sets SS:SP to CS:0x6b49, the top of the zero-filled hole (**inferred**: a private stack in the ROM's RAM copy). The 6.5.30 entry does the same (stack top 0x6552 there).
3. **Scratch registers (0x86d, table at 0x875).** **Established.** Through the register script: writes 0 to registers 0x20, 0x24, 0x28 and 0x2c (`BIOS_4_SCRATCH` to `BIOS_7_SCRATCH`), then register 0x10 (`BIOS_0_SCRATCH`) AND 0xfffffffb, OR 4. The three-line table is the same data as in 6.5.30.
4. **ASIC init 1 (`0x6b6c`, table 0x2a7, 46 entries).** **Established**, **observed** in order. In the register order of [init-scripts.md](init-scripts.md#asic-init-1-header-slot-0x0c-table-at-0x2a7-46-entries-run-first): `BUS_CNTL` (0x30) first written 0x5133a2a0, then AND 0xffffffef; 0xec = 0x444f; `CRTC_GEN_CNTL` (0x50) = 0x4000000; `DAC_CNTL` (0x58) = 0xff000002; `DAC_EXT_CNTL` (0x280) = 0; `DAC_CNTL2` (0x7c) = 0; register 0x888 = 0; register 0x168 AND 0x7fffffff; register 0x188 OR 0x923def; register 0x178 = 0x7020; register 0x17c = 0xcb30cb3; then the memory-controller indirect writes (index 0x124, 0x118, 0x119, 0x11b, 0x11d, 0x11f, 0x121, 0x11a, 0x11c, 0x11e, 0x120, 0x126, 0x12f, then index 0 to park the window); `DISP_MISC_CNTL` (0xd00) AND 0xffffff OR 0x5b000000; `SEPROM_CNTL1` (0x1c0) AND 0xffffff OR 0x6000000; 0xaa0 = 0x60012375; 0x118 = 0x8bbbb; `SEPROM_CNTL1` again. The entries for `BUS_CNTL`, `CRTC_GEN_CNTL`, `DAC_CNTL` and `DAC_CNTL2` use the direct window; the rest the index window.
5. **VGA and vector set-up (0x899).** **Established.** When the PMID block's in-protected-mode word (0x5a16) is zero it first stores CS in the block's code-segment selector word (0x5a14). Then: writes 5 to port 0x3c2 (VGA miscellaneous output), reads ports 0x3da and 0x3ba, writes 0 to 0x3c0 and 0x2001 to 0x3c4. With interrupts off it then sets real-mode vectors: 0x42 to F000:F065 (the system BIOS's own video handler, kept for chaining); 0x1f to cs:0x2cb6; 0x43 to cs:0x30c9; 0x10 and 0x6d both to cs:0x1eba (the ROM's video interrupt handler, [int10-vesa-services.md](int10-vesa-services.md)); and the word pair at linear 0x4a8 (the video save pointer) to cs:0x1f2e. It stores CS into the segment halves of the pointer words at cs:0x1f30, 0x1f40 and 0x1f52. **Inferred:** 0x2cb6 and 0x30c9 are the 8x8 and 8x16 character tables (the font's smiley glyph is at 0x30db).
6. **Main set-up (0x7ba).** **Established.** In this order:
   1. **PLL init**: the PLL script (`0x7096`, table at 0x589, 64 entries), decoded in [init-scripts.md](init-scripts.md#pll-init-slot-0x46-table-at-0x589-64-entries).
   2. **ASIC init 2 (`0x6b4a`)**: with interrupts off, the register script over the table at 0x3de (32 entries); then it reads register 0x3428 (`RB2D_DSTCACHE_MODE`), ORs bit 17 and writes the result to register 0x1710 (`FLUSH_4`). Why one register's value goes to another is **unknown**, as in 6.5.30. **Observed** values in [init-scripts.md](init-scripts.md#asic-init-2-slot-0x4e-table-at-0x3de-32-entries).
   3. **Memory-mode sequence (`0x715f`)**, below.
   4. **Memory size (0xa842).** **Established.** Sets bit 26 of `CRTC_GEN_CNTL` (the byte at `P+0x53`, bit 2); writes 0x2a to lane 0 of register 0x140 (`MEM_CNTL`); writes the word 0x1000 to `P+0xfa`, the upper half of `CONFIG_MEMSIZE` (0xf8); clears bit 26 and sets bit 25 of `CRTC_GEN_CNTL`; waits 15 times 2 ms. The 0x1000 is a literal, not a probed size. **Inferred:** as the upper half of a byte count it is 0x10000000, 256 MB.
   5. **Second DAC and TV DAC test (`0x7e00`).** **Established** by reading; **observed** values below. Sets bit 7 of `P+0x55` (`CRTC_EXT_CNTL` lane 1), writes `DAC_EXT_CNTL` (0x280) = 0x1b630 OR 0xc0 and then 0x1b630 OR 0x40 (each pass followed by writing 0), with bits in `DAC_CNTL` (`P+0x58`) set and restored and a 2 ms wait; then sets bit 0 of `GPIOPAD_EN` (0x1a0), `GPIOPAD_MASK` (0x198) and `GPIOPAD_A` (0x19c), writes `DAC_CNTL2` (0x7c) = 2, `CRTC2_GEN_CNTL` (0x3f8) = 0xc0, `DAC_EXT_CNTL` = 0x180c3 and `TV_DAC_CNTL` (0x88c) = 0x680200 then 0x680213, reads lane 3 of 0x88c, and restores 0x88c, 0x280, 0x3f8, 0x7c and 0x19c. Two bytes of the result go to `P+0x20` and `P+0x21` (low bits). It has the shape of a presence test for the second DAC and the TV DAC; the field meanings are **unknown**. Same routine, same values as in 6.5.30.
   6. **Monitor detection (`0x9d01`)**, below. **Only in the 6.5.22 images.**
   7. **Dynamic clock script**: the PLL script over the table at 0x65b (9 entries), [init-scripts.md](init-scripts.md#dynamic-clock-script-slot-0x52-table-at-0x65b-9-entries).
   8. **`0x828`.** Reads the word at `P+0x20`; if none of the bits 0xb3f is set it sets bit 1 of its low byte; from the two bytes it picks 2, 8, 0x20 or 0x80 and stores it AND 0xab in the byte at `P+0x27` (the top byte of `BIOS_5_SCRATCH`). **Established**; the bit meanings are **unknown**. **Observed** with the model: `P+0x20` becomes 2 and `P+0x27` becomes 2.
   9. **`0x804`.** **Established.** Sets bits 4 and 0 in the BIOS data area byte at linear 0x489 and keeps bits 4, 2, 1 and 0; calls `0x4a69` with AL=1 (sets bit 0 of the miscellaneous output register to 1, read back from port 0x3cc), then sets mono text mode (`0x4b1e`: equipment bits 5:4 = 3, CRTC port 0x3b4 at linear 0x463, `int 0x42` AX=7, the system BIOS's own handler) and colour text mode (`0x4b66`: equipment bits 5:4 = 2, port 0x3d4, `int 0x6d` AX=3), the same sequence as the 6.5.30 routine that follows its monitor tests.
   10. **`0x9946` and `0x9920`.** **Established.** Build a display-combination code pair from bit 1 of linear 0x489, bit 0 of port 0x3cc and whether a CRTC answers at 0x3b4 or 0x3d4, then look it up in the table at 0x99c4 (loop limit 0x10) and store the index or 0xff at linear 0x48a. **Inferred:** the VGA display combination code.
   11. **`0x10f7`.** **Established.** Writes the constants 0, 4, 4, 0x10 and 0 to the five bytes `P+0x18` to `P+0x1c` (via a 0x20-byte frame and the restore routine). **Inferred:** the video-mode flag bytes; what they record is **unknown**.
   12. **`0x5331`.** **Established.** Patches the card's I/O base `P` and its bus/device/function into the protected-mode table at 0x5710 (the words at +8 and +0xa, that is 0x5718 and 0x571a), and stores the high byte of `P` into each 2-byte entry from offset +0xc until a word of 0xffff. **Inferred:** the protected-mode function table's port list.
   13. **`SEPROM_CNTL1` (0x1c0)**: read, bits 31:24 replaced by 0x06, written back (observed: 0x06000000).
7. **Video mode 3 (0x776).** **Established.** A second `int 0x6d` with AX=3 after the main set-up: the ROM's own video interrupt handler sets text mode 3 again (the 6.5.30 init does not repeat it after step 6; its main set-up already ends in the colour text mode set). **Observed** with the model: a standard VGA 80 by 25 text mode: sequencer registers 0x100, 0x01, 0x302, 0x03, 0x204, miscellaneous output 0x67, sequencer reset 0x300, CRTC registers 0x11 = 0x30 then 0x00 to 0x18 = 5f 4f 50 82 55 81 bf 1f 00 4f 0d 0e 00 00 00 00 9c 8e 8f 28 1f 96 b9 a3 ff, graphics controller 0 to 8, attribute registers 0 to 0x14, plus these chip accesses: `DAC_CNTL` byte 3 (`P+0x5b`) = 0xff and byte 1 (`P+0x59`) read and written back, `BIOS_0_SCRATCH` bit 7 set (0x84), `CRTC_EXT_CNTL` byte 3 (`P+0x57`) written 0, and reads of `FP_GEN_CNTL` (0x287) and `CRTC_V_TOTAL_DISP` (0x20a). The model's reads are all zero, so those branches are the all-zero ones.
8. **Title (0x7a2).** **Established.** Prints the title line at 0x80 with `int 0x6d` AX=0x1301 (write string, attribute 7, cursor from `[0x450]`), a count of 0x38 characters in sg2 and 0x39 in sg3 (the visible text plus a terminator; the same counts as 6.5.30).
9. **Checksum fix-up (0x912).** **Established.** In RAM, limits the size byte at offset 2 to 0x80, clears the byte at 0x21, sums the first 0x8000 bytes and stores the two's complement at 0x21, then sums the following (size minus 0x40) times 512 bytes and stores the two's complement in the last byte before 0xa83b (0xa83a in sg2, 0xa803 in sg3; the 6.5.30 images use 0x934f, 0x965f and 0x964f); this makes the image sum 0 again after the run changed bytes of it. Then it pops everything and, unless `cs:[0x6941]` holds 0x3412, restores SS:SP and stores 0x3412 there; returns far.

## Memory-mode sequence

**Established**, **observed** in order. `0x715f` (the 6.5.30 `0x6b12`): first runs the register script at 0x4d2 ("init 4", 25 entries): it writes indirect index 0x11a, 0x11c, 0x11e and 0x120 with 0x151557ff, then waits 10 ticks (script code 4), then clears bits 25:24 of those four registers by read-modify-write, twice. It then reads records from the memory-config table at 0x680 plus 5: a record is a byte cl followed by two data bytes, a lone 0x0f means wait until `MC_STATUS` (0x150) bits 3:0 are all set (the model reads 0xf at once), and 0xff ends. For each cl record the two data bytes go to lanes 0 and 1 of register 0x158 (`SDRAM_MODE_REG`), then lane 3 is read, ANDed with 0x6f, ORed with cl and written back. The 6.5.22 sg2 records give the 16-bit words 0x1000, 0x0042, 0x1042, 0x0142 and 0x0042 in that order, each loaded with cl = 0 and again with cl = 0x80, separated by the `MC_STATUS` waits. After the loop, PLL register 0x15 lane 3 is ANDed with 0x0f and ORed with the byte after the end marker, and the empty script at 0x4d0 ("init 3") runs. **Inferred:** a DDR-style power-up sequence that loads the memory device's mode registers through `SDRAM_MODE_REG`, with bit 7 of lane 3 as the load strobe; the bit and word meanings are **unknown** (no public document for this chip lists the fields; the Linux header names only the register). The sequence and values are the same in the 6.5.30 images.

## Monitor detection (6.5.22 only)

**Established** for the routines and accesses listed; roles are **inferred** unless stated. The 6.5.22 images run monitor detection at init and carry a software DDC transfer that the 6.5.30 images do not; the 6.5.30 images keep a DDC read behind vendor function 0x0b (`0x5dbb` in sg2), whose transport was not read in this pass (of the 113 routines the walk reaches from the sg2 entry, 64 are identical in shape to a 6.5.30 routine and 49 are not: three are changed versions of 6.5.30 routines (the entry, the main set-up and `0x10f7`), the others are this subsystem; sg3 is the same with 43 of 109; [differences.md](differences.md#6522-against-6530)). Called from the main set-up in step 6.6 (`0x9d01` in sg2, `0x9cc4` in sg3).

- **Probe ports.** `0x9bff` and `0x9c22` clear bit 3 of the byte at `P+0x20` and `P+0x21` respectively, call the DDC transfer primitive (`0x6270`) with BH = 2 and BH = 6 (BL = 0), and when it reports something and the low two bits of the byte are clear, set bit 3 again. **Inferred:** bit 3 of those scratch bytes records "a monitor answered on this port". `0x9caf` clears bit 3 of `P+0x21` and bit 2 of `FP2_GEN_CNTL` (0x288).
- **DDC transfer primitive (`0x6270`).** BH selects the port: 2 and 0 use the GPIO record at 0x5d03 (`GPIO_VGA_DDC`, register 0x60), 4 uses the record at 0x5d1d (`GPIO_DVI_DDC`, register 0x64), 6 has no record in the image (its pointer word is zero). BL is a command (0x81 reads 0x80 bytes). **Established** for the dispatch and the two records; the records hold the register index twice-over and a few bit numbers, not decoded here. In sg2 the transfer is a software bit-bang: the routines at 0x5d59 to 0x5ff9 toggle and sample bits of the GPIO register through byte accesses at `reg+0` to `reg+2` (**observed** in the model run: `GPIO_VGA_DDC` accessed as 0x60, 0x61 and 0x62 bytes in loops; the run does not finish a transfer because every sample reads zero, and spends about 30000 of the 33442 logged events there). In sg3 the transfer instead uses the chip's second I2C engine: registers 0x2e0, 0x2e4 and 0x2e8 (`DVI_I2C_CNTL_0`, `DVI_I2C_CNTL_1`, `DVI_I2C_DATA` in the Linux header), writing the control value 0x27 to 0x2e0, 0x20020011 to 0x2e4, the 8-bit slave address to 0x2e8, and the command 0x7801100 or 0x7801700 to 0x2e0, then polling 0x2e0 until its low three bits read 1 (3:1 clear: pending; bit 1 or 2 set: error). The status poll is routine `0x5ce7`; it uses register 0x90 (`I2C_CNTL_0`) instead when the carry flag is set. **Observed** slave addresses in the sg3 model run: 0xa0, 0xa1, 0xa2, 0xa3, 0xa6, 0xa7 (the 8-bit write and read forms of 0x50, 0x51 and 0x53, **inferred** as DDC EDID EEPROM probes).
- **Reading and recording the monitor data.** `0x99fc` (182 instructions) asks for 0x80 bytes with BL = 0x81 and, if the first byte is 0x20, looks four bytes at offset 1 up in a table of 6-byte records at 0xa829 (end marker 0xffffffff) and stores the matching word at 0x99fa; it then makes a second transfer call with ECX = 0x01800100 (what those two halves select was not worked out). `0x9bad` copies the 18 bytes it leaves on the stack into the buffer at 0x99e8 (**established**; the 18-byte buffer is zero in the file). `0x9d7d` copies or rebuilds an 18-byte record (the size of an EDID detailed timing descriptor; the field layout was not compared, so reading it as one is **inferred**). `0x9d4f` maps a word built from bytes 2 and 4 of such a record to a one-hot bit mask through the 8-word table at 0x9bef (0 if there is no match).
- **What it feeds.** The DFP info slot points at the buffer at 0x99e8 ([images-and-tables.md](images-and-tables.md#dfp-info-slot-0x34-6522-only)); the video mode set (video function 0 and the VBE mode set) has extra checks in 6.5.22 that call `0xa097`, `0xa0a4` and `0x63e7`, which 6.5.30 lacks (**established** by comparing the two handlers). **Observed** (model run): VBE function 0x15 reaches the same primitive (it accesses `GPIO_VGA_DDC`); the 6.5.30 ROM also has a function 0x15 handler, and how that one reaches a monitor was not read in this pass. Which timing records a given monitor selects is **unknown**.
- **Grade of the whole.** The existence of the subsystem, its calls and the registers named are established; that it reads the monitor's EDID is **inferred** from the 18-byte descriptor layout, the 0x80-byte block size and the slave addresses; **unknown:** the contents of the 6-byte table at 0xa829 and what the byte value 0x20 marks.

## sg3 external transmitter

**Established.** `0x621e` (the 6.5.30 `0x5f7d`): sets bit 10 of registers 0x1b0, 0x1a8 and 0x1ac (`MDGPIO_EN`, an unnamed register and `MDGPIO_A` in this repository's display unit), waits 15 times 4 ticks, clears bit 10 of 0x1ac; walks the external TMDS table at 0x61e4 and sends each (register, value) pair; then writes register 0x288 (`FP2_GEN_CNTL`) = 0x1240080c and PLL register 0x2d = 0x02040000. **Difference from 6.5.30:** in 6.5.22 sg3 this routine is called from the entry (after the main set-up and before the mode-3 set), and the transaction goes through the generic I2C routines (`0x5eb5`, `0x6066`, `0x611b`) rather than the dedicated routine of 6.5.30; in 6.5.30 it is called from inside the main set-up. **Observed** with the model: the I2C engine at 0x90, 0x94 and 0x98 is used (`I2C_CNTL_0` = 0x27, `I2C_CNTL_1` = 0x20020012, the data port 0x98 loaded, `I2C_CNTL_0` = 0x7801310), and the first transaction's three data bytes are 0x70, 0x08, 0x39 (slave address, register, value), as the table says. In the following four transactions the model run's first data byte is the previous transaction's register (0x08, 0x0a, 0x0c, 0x09) instead of 0x70; the 6.5.30 model run sends 0x70 every time. Whether that is a defect of the 6.5.22 routine or an artefact of the model (for example a register the routine reloads from a status flag the model does not produce) is **unknown**: the routine's table walk is not fully read.

## Differences from the 6.5.30 init

**Established** unless marked:

| | 6.5.22 | 6.5.30 |
|---|---|---|
| Init entry | 0x6e4 (sg2), 0x6e9 (sg3) | 0x6c8, 0x6d3 |
| Host bridge fix (PCI-AGP bridge 8086:2552, configuration offset 0x70 bit 9) | absent | present, before the checksum fix-up |
| Monitor detection at init, bit-banged DDC transfer | present | absent (a DDC read stays behind vendor function 0x0b) |
| Extra `int 0x6d` AX=3 text mode set after the main set-up | present | absent (the mono and colour text sets inside the main set-up are in both) |
| Internal TMDS and PLL programming in ASIC init 2 | present | replaced by flat-panel register clears |
| sg3 external transmitter | called from the entry, generic I2C | called from the main set-up, dedicated I2C routine |
| Script values | [init-scripts.md](init-scripts.md#what-changed-from-6522-to-6530) | |

**Established.** The host bridge fix of 6.5.30 (it reads configuration dword 0 of bus 0, device 1, function 0 and, for 0x25528086, sets bit 9 of configuration offset 0x70) is not in the 6.5.22 images (no call to a configuration write exists in the entry). Its effect is **unknown** ([option-roms.md](../../software/ucode/option-roms.md#the-init-entry-sg2-addresses-sg3-and-sg3a-in-the-table-below)).
